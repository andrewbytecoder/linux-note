大家好，这一节讲 NodeLocal DNSCache。它不是替换 CoreDNS，而是在每个节点放一个轻量缓存代理，让 Pod 的 DNS 查询先走本机。

今天最重要的不是背一个 DaemonSet，而是看懂透明接管：Pod 的 resolv.conf 仍然写 10.96.0.10，iptables raw 表先把包标成 UNTRACKED，内核再把这个地址当本地地址交给缓存进程。

02

标准路径里，Pod 先发给 kube-dns ClusterIP，再由 kube-proxy 把流量 DNAT 到某个 CoreDNS Pod。这个 Pod 可能在另一台节点上。

DNS 单次报文很小，但调用频率高。延迟、conntrack 压力和偶发 UDP 丢包累积起来，就会变成应用启动慢、服务发现超时或者明显的 P99 抖动。

03

这里要先纠正一个常见说法：NodeLocal 不是“每台机器部署一份 CoreDNS 权威服务”。它使用 CoreDNS 插件框架，但角色是缓存代理。

Service 和 Pod 记录仍然由原来的 CoreDNS 回答。NodeLocal 只保存最近答案，在 TTL 有效期内直接返回。

Why it exists

它同时优化时延、连接跟踪与可观测性

01

本地命中

同名查询直接从节点缓存返回，减少网络跳数。

02

绕开 DNAT

Pod 到本地缓存的 DNS 包使用 NOTRACK，不占用普通 Service NAT 路径。

03

TCP 回源

集群域 miss 可用 TCP 访问 CoreDNS，连接关闭后 conntrack 更快清理。

04

负缓存

短时间缓存 NXDOMAIN，抑制错误域名造成的查询风暴。

05

节点级指标

每个 Node 都有 hit、miss、request、entry 指标。

06

故障域更小

已有缓存可吸收部分上游短时抖动，但不能永久替代上游。

04

最直观的收益是低延迟，但真正值得关注的还有 conntrack。Pod 发往本地缓存的包不做普通 Service DNAT；NodeLocal 到 CoreDNS 的 miss 又可以强制使用 TCP。

另外，指标被拆到节点维度，排查“只有某一台机器 DNS 慢”会更直接。

Positive and negative cache

success 与 denial 使用不同 TTL 控制新鲜度

SUCCESS CACHE9984 entries30 seconds

已有记录的正常响应，减少重复查询。

DENIAL CACHE9984 entries5 seconds

NXDOMAIN / NODATA 短暂缓存，避免错误名称持续打到上游。

为什么负缓存更短

刚创建的 Service 不应被旧 NXDOMAIN 长时间遮住。

容量不是内存上限

每个 server block 都有缓存，内存还受并发查询 goroutine 影响。

17

success 允许 9984 条，默认最多 30 秒；denial 也是 9984 条，但只有 5 秒。负缓存短，是为了让新建 Service 很快可见。

官方估算单个 10000 条缓存满载约 30MB，但 NodeLocal 有多个 server block，并发查询也会占内存，所以不能只给 5Mi request 就认为上限是 5Mi。

这一页把整条链串起来。Pod 包进入节点 namespace 后，raw PREROUTING 最先命中 NOTRACK；nat 里的 kube-proxy 规则虽然存在，却不能对这个 untracked 流完成 NAT。

目标仍是 10.96.0.10，路由表又认定它是本机地址，所以进入 INPUT 并交给监听 53 的 NodeLocal。

规则覆盖 PREROUTING 和 OUTPUT，是为了处理从 Pod 进入以及节点本机发出的查询；每个地址又同时覆盖 UDP 和 TCP 53。

实际输出可能包含额外 match 模块或链名细节，但核心证据是目标地址、协议、端口和 NOTRACK target。

Why raw comes first

NOTRACK 的目的不是加速，而是阻止 kube-proxy 抢走目标地址

01

标记 UNTRACKED

conntrack 不为 Pod→NodeLocal 的 DNS 包维护普通连接状态。

02

NAT 无法建立映射

DNAT 依赖连接跟踪保存正反向地址转换。

03

目标保持不变

dst=10.96.0.10 继续进入路由决策。

04

本地监听胜出

内核发现该 /32 属于本机，交给 NodeLocal。

精确表述：不是“删除 kube-proxy 规则”，也不是“NodeLocal 优先级更高”；是 raw 表先决定不跟踪，让后续 nat 无法为该包建立转换。

27

NOTRACK 经常被简化成“减少 conntrack”，这没错，但在本课透明模式里更关键的作用是让 Service DNAT失效。

所以排障时不能只找 NodeLocal 进程。raw 规则丢失后，查询很可能仍然成功，却直接去了 CoreDNS，缓存完全被绕过。

Validate step 3

kube-proxy 的 kube-dns DNAT 规则仍然存在

这一步专门证明 kube-proxy 没被改坏。KUBE-SERVICES 规则还在，其他普通 Service 也继续照常使用 DNAT。

透明接管只是让匹配 NodeLocal 目标的 DNS 包先变成 untracked，而不是全局关闭 kube-proxy 或 conntrack。

Operational sizing

缓存容量、并发与 OOM 都必须按节点评估

MEMORY

约 30MB / 10000 entries / server block

官方给的是量级估算，不是硬上限；多 zone 会叠加。

CONCURRENCY

查询 goroutine 也占内存

上游慢时并发堆积，峰值内存可能明显增加。

OOM

Pod 重启期间有短暂空窗

DaemonSet 会拉起新进程，但 DNS 可短时失败。

RULE LIFECYCLE

异常退出要检查残留规则

进程不可用而透明规则仍在时，查询可能被送到无人监听的本地地址。

课程清单只声明 requests: memory 5Mi，它不是 usage limit。生产应基于指标设置合理 request/limit，并预留查询突发。

42

缓存满载内存是按 server block 估算的，再加上并发请求，生产不能简单沿用 5Mi request。

NodeLocal 崩溃时故障是节点局部的，但这台节点上的 Pod 都依赖它。监控要覆盖 Pod ready、重启次数、内存、请求错误和规则一致性。
