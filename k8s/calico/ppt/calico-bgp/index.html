动态方块代表链路上真实可以流动的包。建立 BGP 时会有 TCP 179 的 SYN、OPEN、KEEPALIVE；后面访问 VIP 时，数据包也会从这些物理连线进入某个节点。

BGPConfiguration + BGPPeer

一个定义“我是谁”，一个定义“我要找谁”

BGPConfiguration · 集群级默认值

apiVersion: projectcalico.org/v3
kind: BGPConfiguration
metadata:
  name: default
spec:
  logSeverityScreen: Info
  asNumber: 65010
  nodeToNodeMeshEnabled: false

关键解释：关闭默认 full mesh，节点之间不再自动互相建立 iBGP。

BGPPeer · 外部邻居定义

apiVersion: projectcalico.org/v3
kind: BGPPeer
metadata:
  name: bgppeer-arista
spec:
  peerIP: 10.10.10.1
  asNumber: 65001
  nodeSelector: all()

关键解释：all() 让三个节点分别与 cEOS 建一个 eBGP Session。

05

BGPConfiguration 是全局默认配置。AS 65010 就是三个 Calico 节点对外报的身份。nodeToNodeMeshEnabled false 表示我们不让节点自动全互联。现场每个 BIRD 实例因此只看到一个外部邻居。

BGPPeer 则明确写出对端 10.10.10.1、对端 AS 65001，并用 all() 选中所有节点。最终不是一条会话，而是三个节点各有一条到 cEOS 的 eBGP 会话。

Peer Group + Listen Range

cEOS 用 listen range 接住三个邻居

router bgp 65001
   router-id 10.10.10.1
   bgp listen range 10.10.10.0/24 \
      peer-group CALICO-K8S remote-as 65010
   neighbor CALICO-K8S peer group
   neighbor CALICO-K8S remote-as 65010
   address-family ipv4
      neighbor CALICO-K8S activate
      network 10.10.10.0/24

为什么用 peer-group + listen range

不用逐个写三段 neighbor。只要来源属于 10.10.10.0/24，远端 AS 又是 65010，就套用 CALICO-K8S 模板。

容易讲错的一行

network 10.10.10.0/24 是 cEOS 对邻居发布本地 VLAN 前缀，不等于 Calico 已经发布 Pod 路由。

06

交换机端的配置很经典。router bgp 65001 建立进程，router-id 是 10.10.10.1。listen range 相当于告诉 cEOS：这个网段里只要有人带着 AS 65010 来敲门，就套用 CALICO-K8S 模板。

最后的 network 10.10.10.0/24 是交换机发布自己直连的 VLAN 网段。不要用它证明 Pod CIDR 已经发布，那是另一件事。

TCP/179 与 BGP 状态机

BGP 建邻：先 TCP，再交换 OPEN

worker-2AS 65010

Connect

07

建邻不是发几个 UDP 包就结束。BGP 基于 TCP 179。TCP 建好以后，双方用 OPEN 报自己的版本、AS、hold time 和 router-id。参数能接受，就进入 OpenConfirm，再靠 KEEPALIVE 进入 Established。

三个节点会重复同样的流程，因此 cEOS 上最终看到三个邻居。排错时，Idle 或 Active 往往指向 IP 可达、TCP 179、防火墙或 ASN 不匹配；Established 才说明通话建立成功。

为什么同时有 blackhole

本地 block 的 blackhole 防止某个不存在的 Pod 地址被默认路由带出；已存在的 workload /32 路由优先级更高。

12

Calico IPAM 不会给每个 Pod 都向全网发布一条路由，而是先把地址池按 block 分给节点。本实验是 /26，所以每个节点用一条聚合路由就能代表本机工作负载。

本地 block 配一条 blackhole，具体 Pod 再用更长的 /32 路由覆盖。这样既避免地址不存在时漏到默认路由，又能减少跨节点路由数量。

为什么是 blackhole

BIRD 用静态聚合前缀作为广告源，避免为地址池中的每个 VIP 创建一条 BGP NLRI。

为什么节点内核看不到 /28 路由

这里的 static blackhole 是 BIRD 路由表中的广告源。节点内核的 ip route show 172.16.0.240/28 没有输出，VIP 的本地接收由 kube-proxy iptables 实现。

从 1 条 FIB 路径到 3 条 ECMP

配置

15

这条链路可以分四段。cEOS 发给实际 VIP 172.16.0.240，当前 FIB 通过 10.10.10.10 把包送入 control-plane。kube-proxy 的 iptables 规则命中 KUBE-EXT 链，再转入 KUBE-SVC。

KUBE-SVC 用 50% 概率选择 192.168.164.138:80，另一条规则选择 192.168.81.66:80，最终通过 KUBE-SEP 做 DNAT。cEOS 直接 curl VIP 返回 HTTP 200。

Service manifest 没有写 externalTrafficPolicy，所以默认是 Cluster。即使流量先到没有 nginx Pod 的 control-plane，kube-proxy 仍可选择 worker 或 worker2 上的 Endpoint；这会产生第二次跨节点转发，并通常对源地址做 SNAT。

为什么入口节点可以没有本地 Pod

externalTrafficPolicy=Cluster，KUBE-SVC 可以选择全局任意 Ready Endpoint；因此 control-plane 收到包后仍能转发到 worker 或 worker2。

cEOS 只把数据包送到一个 Kubernetes 节点。节点上的 KUBE-SERVICES 先匹配 VIP，跳到 KUBE-EXT 处理外部流量，再进入 KUBE-SVC 选择 Endpoint。

现场规则显示 worker2 Endpoint 使用 50% 随机概率，未命中就落到 worker Endpoint。最后 KUBE-SEP 将目的地址 DNAT 成真实 Pod IP 和端口。

补充知识 · 官方行为边界

externalTrafficPolicy 决定“哪些节点发布”和“进来后去哪”

维度Cluster（当前 manifest 默认）Local
BGP 广播节点所有未排除的节点广播 Service CIDR只有拥有本地 Endpoint 的节点广播 Service 的精确路由
上游负载分担ECMP 可打到任意节点ECMP 只打到真正托管后端的节点
二次跨节点可能发生对 LoadBalancer / NodePort 可避免
客户端源 IP通常被 SNAT 隐藏保留原始源 IP
代价后端分配更均匀，路径可能更长流量可能不均，但路径短，策略更直观

本实验结论：Service 未显式设置 externalTrafficPolicy，因此采用 Cluster。三个节点都会发布 /28，即使 control-plane 没有本地 nginx Endpoint。

16

默认 Cluster 模式下，所有节点都能接流量，kube-proxy 可以选择全局任意健康 Endpoint，因此可能再跨一次节点，也可能 SNAT。

Local 模式只让真正有本地 Endpoint 的节点发布更精确的 Service 路由，外部源 IP 得以保留，也避免第二跳。不过 Pod 分布不均时，上游看到的容量也可能不均。今天的实验没有写这个字段，所以明确按 Cluster 模式讲。

BGP Withdraw + ECMP 收敛

一条路径撤销，剩余入口继续服务新连接

cEOS172.16.0.240/28
via .10control-plane
withdraw .11worker
via .12worker2

控制面

BGP 会话断开或路由撤销后，cEOS 从 RIB 删除 .11 路径。

转发表

ECMP group 缩减到 .10 与 .12；新流量重新按剩余成员哈希。

连接影响

经过故障节点的既有连接可能中断；其余路径不会自动迁移旧 TCP 状态。

Local 模式差异：只有承载本地 Endpoint 的节点发布精确路由，Pod 调度变化也可能触发前缀新增或撤销。

27

ECMP 提供的是入口冗余，不代表已有 TCP 连接可以无缝漂移。节点 .11 故障后，cEOS 删除对应路径，新连接继续从 .10 或 .12 进入。

故障检测速度由 BGP 定时器、TCP 会话状态、BFD 等机制决定。本实验 hold time 是 180 秒；生产环境如果要求更快收敛，需要单独设计快速检测，而不是盲目缩短所有定时器。

总结

把整套实验压缩成一条因果链

节点 eth1 与 cEOS 二层可达，三个 eBGP Session 建立；Calico IPAM 分配 VIP 172.16.0.240；三个节点发布同一 /28；cEOS 当前选择 .10 作为最佳入口；kube-proxy 再把 VIP 转给 nginx Pod。
会话

Established 表示控制通道可用。

前缀

PfxRcd=1 表示 /28 已被收到。

路径

RIB 有 3 条，当前 FIB 装 1 条；maximum-paths 可开启 ECMP。

业务

HTTP 响应才是最终端到端证据。

最后一句：BGP 负责把“VIP 在哪里”告诉网络，Kubernetes Service 负责把“VIP 后面是谁”落实到 Pod。

19

最后把逻辑收回来。BGPPeer 与 BGPConfiguration 先回答谁能和谁交换路由；LoadBalancer IPPool 和 serviceLoadBalancerIPs 再回答 VIP 从哪里分配、向外发布哪条 Service 路由。

外部包进来后，BGP 的工作已经基本完成，接下来交给节点路由、kube-proxy 和 Pod。现场 cEOS 与 multitool 都已得到 HTTP 200，证明这条链路完整闭环。
