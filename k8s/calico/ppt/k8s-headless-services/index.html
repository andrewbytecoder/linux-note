大家好，这一节我们讲 Headless Service。它最关键的变化只有一行：clusterIP: None，但这行配置会把服务发现和流量路径都改掉。

普通 ClusterIP 是 DNS 返回一个虚拟 IP，再由 kube-proxy 选后端；Headless Service 是 DNS 直接返回 Pod IP，由客户端决定连谁。拿到 Pod IP 后，真正承载流量的仍然是 Calico 的 Pod 网络。

主课程：https://k8snetworking.com/lessons/11-headless-services

No VIP, direct discovery

Headless 到底省掉了什么

spec.clusterIP: None
∅

没有 Service VIP

API 不为它分配 ClusterIP，客户端不会把业务流量发往一个虚拟地址。

DNS

返回 Endpoint 地址

CoreDNS 根据 EndpointSlice 返回一组 Pod IP，而不是一个 Service IP。

↗

客户端直接连接

选中地址后直接走 Pod 路由；负载选择留给客户端或上层系统。

一句话：Headless Service 不是“没有 Service 对象”，而是“这个 Service 不提供 VIP 代理入口”。
02

Headless 不是把 Service 删除了。Service 对象仍然存在，selector、port、DNS 名称也都存在，只是没有 ClusterIP。

因此它仍然能驱动 EndpointSlice 和 DNS 服务发现，但业务流量不再经过 Service VIP。客户端从 DNS 结果里选一个 Pod IP，然后直接连接。

ClusterIP

kube-proxy 编程 iptables/IPVS，把 VIP 流量 DNAT 到 Endpoint。

Headless

没有 VIP 和对应 NAT 规则，连接直接命中 Pod IP。

03

这两条路径使用相同的 selector，后端甚至可以是同一组 Pod，但前半段完全不同。

ClusterIP 的客户端只看到 VIP，后端选择由 kube-proxy 数据面完成。Headless 的客户端看到一组地址，自己选择后端；所以这里没有免费的平台侧负载均衡。

为什么可扩展

大量 Endpoint 可以拆分到多个 Slice；每个 Endpoint 还包含 readiness、hostname、nodeName、zone 等元数据。

精确表述：EndpointSlice controller 根据 Service selector 维护后端；CoreDNS watch EndpointSlice 并组织 DNS 应答。
13

DNS 不是直接扫描 Pod。控制器先把符合 selector 的 Pod 写进 EndpointSlice，CoreDNS watch 这些 Slice。

对 Headless Service，CoreDNS 从 EndpointSlice 读取地址，返回 Pod IP。对 StatefulSet，Slice 中的 hostname 还让 CoreDNS 能构造每个 Pod 的稳定 DNS 记录。

Address and service records

A、AAAA 与 SRV 分别告诉你什么

A

IPv4 地址

redis-headless → 192.168.x.x

课程实验主要看到这一类。

AAAA

IPv6 地址

service → Pod IPv6

双栈/IPv6 集群按地址族返回。

SRV

端口 + 主机名

_redis._tcp.redis-headless...

命名端口会生成 SRV 记录；Headless 可返回每个 Pod 目标。

dig SRV _redis._tcp.redis-headless.default.svc.cluster.local
21

A 记录返回 IPv4，AAAA 返回 IPv6。SRV 记录同时携带端口和目标主机名，前提是 Service port 有名称，这里端口名就是 redis。

应用是否真正使用 SRV 取决于客户端库。不能因为 DNS 存在 SRV 记录，就假设普通 Redis 客户端会自动发现整个集群。

VIP NAT rules

没有 ClusterIP，就没有可匹配和 DNAT 的 Service VIP。

“绕过 kube-proxy”指业务连接不经过 Headless Service VIP；它仍然依赖 Kubernetes 控制面和 CoreDNS 完成发现。

Operational gotchas

Headless 交还给客户端的四个责任

01

地址选择

DNS 返回多地址，不代表客户端会均匀使用全部地址。

02

缓存与 TTL

课程示例 TTL 30 秒；客户端缓存策略可能让旧地址停留更久。

03

Pod churn

Pod IP 会变化，客户端必须重解析、重试并丢弃失败连接。

04

就绪语义

默认 DNS 发布 Ready Endpoint；成员启动互相依赖时评估 publishNotReadyAddresses。

负缓存：Pod 出现前查询失败，NXDOMAIN 可能被缓存；StatefulSet 官方文档提醒新 Pod 的名称不一定立刻可查。

34

Headless 把选择权交给客户端，也把四个责任交回客户端：选地址、处理缓存、应对 Pod 地址变化、理解 Endpoint readiness。

如果多个成员必须先互相发现才能 Ready，可以评估 publishNotReadyAddresses，但这会让未就绪地址也进入发现结果，需要应用自己能处理连接失败。

Troubleshooting ladder

沿证据链找第一个断点

1

对象存在吗

kubectl get svc,sts,deploy

先核对名称、namespace、selector。

2

Endpoint 正确吗

kubectl get endpointslice -o yaml

看地址、ready、hostname、targetRef。

3

DNS 怎样回答

dig +search / dig FQDN

区分 NXDOMAIN、无答案和超时。

4

Pod IP 可达吗

nc / redis-cli / curl

验证 Calico 路由、策略与端口。

5

应用角色正确吗

INFO replication / logs

DNS 正确不代表应用状态正确。

6

缓存过期了吗

TTL / client cache

重建后旧连接和旧解析可能仍存在。

36

排障从 Kubernetes 对象开始，沿 EndpointSlice、DNS、网络和应用逐层推进。第一个不符合预期的层就是当前重点。

最常见的错误是 selector 不匹配、Endpoint not ready、serviceName 拼错、客户端缓存旧地址，或者 DNS 正确但 NetworkPolicy 和应用端口阻断连接。

A practical decision tree

选 ClusterIP 还是 Headless

客户端需要指定具体实例或发现所有成员吗？

否

优先 ClusterIP

让 kube-proxy/数据面负责透明后端选择。

普通 Web / API
是

考虑 Headless

客户端直接消费 Endpoint 地址集合。

数据库 / P2P / 自定义 LB

还需要稳定单实例名称？

搭配 StatefulSet，并让 spec.serviceName 指向 Headless Service。

常见组合不是二选一：同一 StatefulSet 可以同时提供 Headless Service 做成员发现，再提供普通 Service 做统一读写入口。

37

判断标准不是“有状态就一定 Headless”，而是客户端是否需要知道具体成员。只想访问任意健康实例时，ClusterIP 更合适。

实际系统经常同时使用两种 Service：Headless 负责成员发现和集群内部通信，普通 Service 负责面向应用的统一入口。
