02

DNS 的价值不是把 IP 隐藏得更漂亮，而是把应用和网络对象生命周期解耦。应用只保存稳定名称，CoreDNS 根据当前 Kubernetes 对象返回地址。

Namespace 也是名称的一部分。短名称只在当前 namespace 内确定，跨 namespace 时需要把 namespace 带上。

03

一次查询可以拆成五段。应用交给 Pod resolver，resolver 根据 search 和 ndots 生成候选名称，然后发给 kube-dns ClusterIP。kube-proxy 把流量送到一个 CoreDNS Pod。

CoreDNS 再决定由 kubernetes 插件权威回答、由 cache 返回，还是交给 forward 插件访问上游。

CoreDNS 是插件链。.:53 表示在 53 端口处理所有 zone，kubernetes 插件对 cluster.local 权威，forward 处理其余名称，cache 放在查询链中减少重复工作。

Authoritative for cluster.local

kubernetes 插件生成集群记录

Headless A / AAAAdb.default.svc.cluster.local

pods insecure

为兼容 kube-dns，可按请求中的 IP 形式返回 Pod A 记录，不验证对应 Pod 一定存在。

ttl 30

kubernetes 插件回答记录的 TTL 为 30 秒。

13

kubernetes 插件读取 Kubernetes API 数据并实现 DNS-Based Service Discovery 规范。普通 Service 名返回 ClusterIP，Headless Service 名返回后端 Pod IP 集合，命名端口还会生成 SRV。

pods insecure 是兼容模式。它可以为形如 10-1-2-3.namespace.pod.cluster.local 的名称返回 IP，而不验证这个 Pod 是否真实存在。需要验证时可以考虑 pods verified，但会增加内存与 API watch 成本。

运行插件的准确职责

课程口径修正：loadbalance 调整回答中的记录顺序；上游选择属于 forward 插件。

15

这页把容易混淆的插件职责讲严谨。health 和 ready 不是 DNS 端口，prometheus 只提供指标，reload 周期检查 Corefile 并优雅重载。

loop 只能在启动阶段检测简单静态环路。loadbalance 随机化回答中的 A、AAAA、MX 顺序，不负责上游 resolver 的轮换。

20

ndots:5 表示名称中的点少于 5 个时，resolver 优先把 search suffix 逐个追加。nginx-service 没有点，所以先尝试当前 namespace 的完整 Service 名。

这能让短名称方便工作，也会让 api.example.com 这类短外部名称先产生多次集群内查询。对延迟敏感时可以使用带结尾点的 FQDN，或谨慎调整 Pod dnsConfig。

环路风险

如果上游最终又指回 CoreDNS，loop 插件可能让 CoreDNS 退出并进入 CrashLoopBackOff。

27

ClusterFirst 不表示外部查询绕过 CoreDNS。Pod 仍然把请求交给 10.96.0.10，CoreDNS 发现不属于 cluster.local 后再用 forward 插件访问上游。

如果 /etc/resolv.conf 指向一个最终又回到 CoreDNS 的本地 stub，就会形成转发环路。loop 插件检测到简单启动时环路后会让进程退出。

28

DNS 常被简化为 UDP 53，但 kube-dns Service 同时暴露 UDP 和 TCP。大应答、截断重试或显式 +tcp 都会使用 TCP。

网络策略和防火墙只放 UDP 53 时，普通查询可能正常，较大响应却失败，这是很典型的间歇性问题。
