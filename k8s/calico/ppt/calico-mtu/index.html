大家好，这一节讲 MTU。它最麻烦的地方，是小包、ping、TCP 建连都可能正常，只有证书、镜像层或者某个大响应一来，连接才开始卡住。

这节课分两段。第一段解决 Pod 接口只有 1450 的本地限制，第二段故意把 VLAN 20 SVI 降到 1500，观察跨 VLAN TLS、PMTUD 和严格 RPF 如何相互影响。

The deceptive symptom

小 ping 正常而 TLS 超时，是典型 MTU 线索

64 B ICMP

ping 正常

报文远小于所有接口 MTU。

TCP SYN / ClientHello

连接开始正常

small packets pass

三次握手和 ClientHello 仍能通过。

TLS certificate data

响应卡住

SSL timeout

较大的 DF 数据包撞上路径瓶颈。

排障信号：“小包能通，大包失败”比“完全不通”更像 MTU 或 PMTUD 问题。
02

MTU 故障经常伪装成 TLS、kubectl exec 或 API 超时。原因是前面的 SYN、SYN-ACK、ClientHello 都很小，真正包含较多证书数据的 TCP 段才超过瓶颈。

所以 ping 默认成功不能证明路径支持大包。后面会用 DF ping 和 tcpdump 把边界直接测出来。

Three related sizes

MTU、帧长与 MSS 是三个不同边界

ETHERNET FRAME

二层帧

包含 Ethernet header、IP packet，线上还会有 FCS 和前导码等开销。

不等同于 IP MTU
MTU

最大 IP 包

接口能承载的 IP header、传输层 header 与 payload 总和。

通常不含 Ethernet header
TCP MSS

最大 TCP 数据

TCP 在一个 segment 中愿意接收的应用数据上限。

IPv4 常用近似 MTU − 40

课程公式按 IPv4、无额外 IP/TCP 选项简化：MSS = MTU - 20 - 20。IPv6 基础头为 40 字节，封装开销也不同。

03

先把三个词分开。MTU 说的是 IP 包，不包含普通 Ethernet header。MSS 只说 TCP payload，不包含 IP 和 TCP header。

1500 MTU 对 IPv4 TCP 常得到 1460 MSS，这是课程里的简化公式。实际还有 TCP options、IPv6 和隧道，内核会按真实头部处理。

CrossSubnet 的意思是同一底层子网不封装，跨底层子网才 VXLAN。worker 到 worker2 是直路由，worker 到 worker3 会封装。

Calico workload MTU 是集群级安全值，不能因为某些节点同 VLAN 就给这些 Pod 单独用 9000，否则 Pod 迁移或访问 worker3 时会出问题。

端到端能力取最小值。当前 Pod eth0 只有 1450，所以它是瓶颈。后面三层即使能到 8950 或 9000，也用不上。

生产设计不要只量一台节点，要看 Pod 可能经过的所有 AZ、VLAN、VPN 和隧道路径。

18

默认 ping 的 data 是 56 字节，加 8 字节 ICMP header，再加 20 字节 IPv4 header，总 IP 包 84 字节。

84 远小于 1450，所以成功只能证明基本路由和策略正常，不能证明 jumbo path 正常。

19

-s 8900 只指定 ICMP data，不包含头；-M do 让内核设置 DF 并严格执行路径 MTU。

错误里明确写 mtu=1450，而且是 local error。这说明包甚至没有离开 Pod，不需要先去交换机抓包。

8928 大于 1450，内核在 Pod eth0 立即拒绝

20

动画只画三段固定区域。8928 字节的 IP 包从进程交给 eth0，接口发现超过 1450 且 DF=1，直接返回 EMSGSIZE。

此时在 Host eth1 或 cEOS 抓不到这三个 Echo Request，因为它们根本没离开 Pod namespace。

8900、8908、8928 分别对应 payload、ICMP 与 IP

+ 8

21

ping 输出的三个数字不冲突。8900 是 -s 指定的数据，回复行的 8908 加了 ICMP header，第一行括号里的 8928 再加 IPv4 header。

跨 VLAN Pod 路径使用 VXLAN，再加 50 后是 8978，刚好在 9000 以内。

Explicit target

9000 underlay 配 IPv4 VXLAN，Pod MTU 取 8950

公式要使用真实路径最小值。任何中间 VLAN、云网络、VPN 或物理口小于 9000，都必须按更小值重新计算。

22

IPv4 VXLAN 的 50 字节包括外层 IPv4、UDP、VXLAN 和 inner Ethernet。9000 减 50，所以显式配置 8950。

不要只看服务器 NIC 标称 9000。路径中最小的 SVI、VPC、专线或 VPN 才是真正分母。

Why TLS reveals the issue

TLS 证书链产生较多数据，更容易暴露错误的 MSS 与 Path MTU

1

small

2

200–500 B

通常仍小于 1500。

certificate data

4

Worker3

waits

关键数据段未到达。

准确理解：TLS 证书链是应用数据，不等于一个固定 4 KB IP 包。真正是否超 MTU，由 TCP 分段、双方 MSS、PMTU 缓存和 offload 共同决定；本实验抓到的是 1664 B DF IP 包。

35

课程用证书链解释为什么 TLS 容易触发问题，这个方向正确。但要说精确一点：TLS message 会交给 TCP 分段，不是固定封成一个 4KB IP 包。

本实验由于端点按 9000 MTU 宣告较大的 MSS，服务端实际发送了超过 1500 的 DF 数据包，抓包示例是 1664 字节。

PMTUD 的核心是让路由器告诉发送端“这个出口只有 1500”。发送端把结果放进 route cache，以后分更小的 TCP segment。

如果 ICMP 被防火墙或 RPF 丢掉，发送端永远学不会正确值，就会出现小包通过、大数据静默超时。

Design checklist

生产 MTU 设计应从最小路径和全部封装模式反推

PATHS

枚举所有路径

同节点、同子网、跨 AZ、专线、VPN、出口网关。

MINIMUM

找最小 underlay MTU

不要只看 NIC，要包含 SVI、云网络和中间隧道。

OVERHEAD

扣除最大封装开销

VXLAN、IP-in-IP、WireGuard 或组合迁移阶段。

CONFIG

显式配置并滚动重建

Operator Installation 或 manifest ConfigMap。

VERIFY

用 DF 大包实测

从多个节点、多个网段验证双向数据面。

MONITOR

监控 ICMP 与重传

关注 Frag Needed、TCP retransmission 和超时。

52

生产设计先列路径，再取最小 MTU，最后减掉可能出现的最大封装开销。配置后要重建 workload，并从不同故障域做 DF 测试。

PMTUD 是保护机制，不是容量规划。ICMP 被过滤、RPF、非对称路由都可能让它失效。
