大家好，这一节我们学习 Calico Multiple IPPools。实验把 192.168.0.0/16 划成两个 /17，普通 Pod 从 Default 池拿地址，指定的 multitool-2 从 Secondary 池拿地址。

Address allocation boundaries

多个 IPPool 提供可控的地址分组

默认分配

192.168.0.0/17

匹配所有节点，未指定地址池的 Pod 从这里分配。

按需分配

192.168.128.0/17

默认不匹配任何节点，只接受显式请求该池的工作负载。

边界：IPPool 只改变地址分配范围，不会自动建立 NetworkPolicy，也不会阻止两个池之间通信。

02

多个池适合把工作负载地址按用途分组，例如给外部防火墙、旧系统白名单或不同租户提供稳定的地址范围。

但地址分组不等于安全隔离。只要路由和策略允许，两个池里的 Pod 仍然可以互通。真正的访问控制要另外配置 NetworkPolicy。

CIDR partition

Pod CIDR 被平均拆成两个 /17

每个 /17 包含 32,768 个地址，Calico 再以 /26 为单位按需分配到节点。

09

/16 增加一位前缀就得到两个 /17。低半段从 192.168.0.0 开始，高半段从 192.168.128.0 开始。

IPPool 是可用地址范围，Block Affinity 才是节点当前持有的分配单元。创建池不会马上给每个节点铺满所有 block。

custom-resources.yaml

Installation 资源声明两个 Workload IPPool

- name: default-ipv4-ippool
  blockSize: 26
  cidr: 192.168.0.0/17
  encapsulation: VXLANCrossSubnet
  natOutgoing: Enabled
  nodeSelector: all()
  disableBGPExport: true
- name: secondary-ipv4-ippool
  blockSize: 26
  cidr: 192.168.128.0/17
  encapsulation: VXLANCrossSubnet
  natOutgoing: Enabled
  nodeSelector: "!all()"
  disableBGPExport: true

两池的封装、NAT 与 blockSize 相同，决定自动分配行为的差异只有 `nodeSelector`。

10

两个池的网络行为完全相同，都使用 VXLANCrossSubnet、natOutgoing 和 /26 block。不同点是 Default 匹配所有节点，Secondary 默认不匹配任何节点。

disableBGPExport 为 true 表示不要把这两个 Workload 池的 CIDR 对外导出。实验里的 BGP 与 LoadBalancer 广告是另外的配置面。

11

把这四个字段放在一起，选池逻辑就清楚了。未指定池时，Calico IPAM 从对当前节点可用的自动池中选择，Default 满足条件。

Secondary 的 `!all()` 让自动流程忽略它，但 Pod 或 Namespace 的 ipv4pools 注解可以显式指定该池。

Selector semantics

!all() 让 Secondary 只接受显式请求

all()匹配所有 Node
!
!all()自动流程匹配零个 Node

没有注解

Secondary 不进入候选池，因此不会创建 Secondary block。

显式注解

工作负载指定池名，注解优先于 IPPool nodeSelector。

12

Calico selector 中 all() 匹配所有资源，前面加逻辑非就是匹配零个。YAML 里感叹号有特殊含义，所以课程把表达式放在引号中。

这里采用的是“默认不参与，显式才使用”的设计。Calico 维护者也说明，Pod/Namespace 注解会优先于 IPPool 的 nodeSelector。

CNI 只在 Pod 网络创建时执行选池。运行中的 Pod 不会因为后来增加注解而原地更换 IP。

13

选池发生在 CNI ADD 阶段。Calico 先看 Pod 注解，再看 Namespace 注解；都没有时才按 IPPool 的自动选择规则处理。

因此课程修改的是 DaemonSet 的 Pod template。模板变化触发滚动重建，新 Pod 才会带着注解重新走 CNI。

这一页区分配置状态和分配状态。IPPool 对象存在，只表示地址范围可用，不表示已经有地址交给节点或 Pod。

Secondary 的自动 selector 不匹配节点，又没有工作负载显式请求，所以 IPAM 没有理由创建 Secondary block。

ipv4pools 注解的值是 JSON 数组字符串

  annotations:

这个值容易写错。外层是 YAML 字符串，字符串内容是 JSON 数组，即使只指定一个池也要保留方括号。

2Namespace annotationPod 没有注解时使用
3Automatic pool selection依据 IPPool nodeSelector

显式注解会覆盖池的 nodeSelector 自动选择行为。本实验正是利用这个优先级请求 !all() 的 Secondary 池。

31

优先级从具体到通用：Pod、Namespace、自动池。Pod 和 Namespace 都有注解时，以 Pod 为准。

这里的覆盖是选池优先级，不表示绕过池存在性、CIDR 合法性或 allowedUses。指定的 IPPool 必须存在并允许 Workload。

Configuration pitfalls

Multi-IPPool 常见配置错误

01

池名拼错

Pod sandbox 创建失败，事件中出现 IPAM 错误。

02

注解格式错误

忘记 JSON 数组或 shell 转义，CNI 无法解析。

03

只改现有 Pod

CNI 不会重跑，IP 保持不变。

04

CIDR 重叠

IPPool 校验失败或地址规划产生冲突。

05

混淆 LB 池

allowedUses 不包含 Workload，不能作为 Pod 池。

06

误把池当隔离

没有 NetworkPolicy 时，跨池通信仍可能成功。

32

排错时先看 Pod Events，很多选池错误在 sandbox 创建阶段就会给出明确原因。

再确认注解落在 spec.template.metadata.annotations，池名准确，池允许 Workload，并且 Pod 确实发生了重建。
