大家好，这一节我们把 Kubernetes Service 从一个 YAML 对象拆成真实的数据路径。客户端访问的是稳定的 ClusterIP，真正接收请求的是两个会变化的 nginx Pod。

我们会先确认 Service 和 EndpointSlice，再从客户端建立连接，最后进入 worker 节点逐条读 iptables。重点不是背链名，而是理解 KUBE-SERVICES 负责匹配 VIP，KUBE-SVC 负责选择 Endpoint，KUBE-SEP 负责 DNAT。

02

Pod IP 可以因为滚动更新、节点故障或扩缩容而变化。客户端如果直接保存 Pod IP，就必须理解这些生命周期事件。

Service 把这个问题隔离开。客户端只访问稳定 VIP 或 DNS 名，EndpointSlice 维护当前可用 Pod。kube-proxy 再把每个新连接转到其中一个后端。

ClusterIP is the default

03

Kubernetes Service 不只有 ClusterIP。NodePort 在每台节点开端口，LoadBalancer 再接外部负载均衡器，ExternalName 只生成 CNAME，Headless 则完全取消 VIP。

本课只深入 ClusterIP。它是默认类型，也是其他多种 Service 类型内部仍会依赖的基础能力。

04

先把责任分开。Service selector 和 Pod readiness 由控制面转换成 EndpointSlice。每台节点上的 kube-proxy watch 这些对象，再把期望状态翻译成节点本地规则。

数据包命中 ClusterIP 后，iptables 或 IPVS 选择一个 Endpoint 并做目的地址转换。地址已经变成 Pod IP 后，Calico 才负责本地或跨节点可达。

小写且不完整的 get 不是合法 HTTP 请求，因此 400 符合预期。

$ printf 'GET / HTTP/1.0\r\nHost: nginx-service\r\n\r\n' \

两种结果都证明连接到达 nginx；200 更适合正式演示。

12

课程使用 telnet 建立 TCP 连接，然后输入小写 get。nginx 返回 400，因为 HTTP 方法区分大小写，而且请求头不完整。这个 400 不是 Service 故障，反而证明请求已经到达 nginx。

正式演示可以再补一个规范 HTTP/1.0 请求，得到 200 OK。这样既保留课程步骤，也避免观众把 400 理解成网络失败。

13

Service 规则不是 kubectl 直接写进 iptables。API Server 保存对象，EndpointSlice controller 根据 selector 和 Pod readiness 维护后端列表。kube-proxy 在每台节点 watch Service 与 EndpointSlice，再同步本地规则。

后端变化时，客户端仍使用相同 VIP。变化发生在 EndpointSlice 和每台节点的 kube-proxy 规则里。

客户端在任意节点访问 VIP，先命中本节点规则；选中远端 Endpoint 后，Calico 再完成跨节点 Pod 路由。

14

kube-proxy 在每个节点运行，因此每台节点都能识别同一个 ClusterIP。Service 没有一台固定的代理服务器，规则直接分布在所有节点内核数据面。

如果本节点规则选中远端 Pod，DNAT 后的目标地址就是远端 Pod IP。后续路径与 Lesson 03 完全相同，由 Calico 的远端 block 路由送到目的节点。

18

KUBE-SVC 链先处理可能需要 masquerade 的来源，然后做 Endpoint 选择。两个后端时，第一条 Endpoint 规则使用 0.5 概率，未命中的剩余连接落到第二条。

这不是每个包交替轮询。选择发生在连接建立阶段，后续包由 conntrack 保持同一个 NAT 映射。

iptables 的 random probability 很容易被讲成逐包轮询。更准确的说法是，新连接的首包参与规则选择，选中 Endpoint 后 conntrack 记录 NAT 状态。

源节点匹配 worker2 的远端 /26，Calico 把包送到目的节点。worker2 再用本地 /32 交给 nginx Pod。这正是 Lesson 03 路径在 Service 后半程的复用。

26

课程 KUBE-SVC 第一条规则只在来源不属于 192.168.0.0/16 时打 MASQ mark。集群内 Pod 访问 Service，源地址通常保留，只修改目的地址。

外部来源、hairpin 或其他需要保证对称回程的拓扑可能需要 SNAT。是否发生要看 mark、POSTROUTING 规则和真实抓包，不能简单说所有 Service 流量都会 SNAT。

Pod NotReady

控制面移除或标记不可用，kube-proxy 不再给新连接选择它。

kube-proxy 本身

不主动发送 HTTP 健康检查，它消费控制面状态。

27

kube-proxy 不会自己 curl nginx。kubelet 根据 readiness probe 更新 Pod condition，EndpointSlice controller 再维护可用后端，kube-proxy只消费结果。

排查 Service 没有后端时，先看 Pod Ready 和 EndpointSlice，不要一开始就重启 kube-proxy。

Additional notes

Session Affinity 与双栈边界

sessionAffinity: ClientIPoptional

同一客户端 IP 在超时时间内倾向固定到同一个后端。它改变选择行为，不改变 VIP 与 Endpoint 模型。

spec:
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 10800
Dual-stack ServiceIPv4 + IPv6

双栈集群可以为 Service 分配两种地址族，kube-proxy 为每个 family 编程规则，EndpointSlice 也按 addressType 区分。

spec:
  ipFamilyPolicy: PreferDualStack
  ipFamilies:
  - IPv4
  - IPv6
28

课程附加说明里提到 session affinity 和双栈。ClientIP affinity 会让同一个客户端在超时时间内固定到某个后端，适合需要简单粘性的应用，但不要把它当作应用层会话共享。

双栈 Service 可以同时拥有 IPv4 和 IPv6 VIP。EndpointSlice 用 addressType 区分地址族，节点数据面分别维护规则。
