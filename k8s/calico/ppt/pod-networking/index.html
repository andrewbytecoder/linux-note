02

先把目标压缩成四件事。第一，Pod 必须有唯一 IP。第二，这个 IP 放在 Pod 自己的网络命名空间里，隔离还在。第三，隔离以后仍然要接入宿主机，所以需要一对 veth。第四，宿主机和其他节点必须知道去这个 Pod 的路。

课程图把 Pod 网络画成一条共享的线，便于理解“Pod 都可达”。Calico 实际采用三层路由，Pod 并没有真的挂在一个二层广播域里。我们后面会用 /32 路由和虚拟下一跳把这件事讲清楚。

页面示例写了 containerlab/pod-network。仓库真实目录为 containerlab/02-pod-network，以本地仓库为准。

# pod-network-no-cni.yaml
networking:
  disableDefaultCNI: true
  podSubnet: "192.168.0.0/16"
  serviceSubnet: "10.96.0.0/16"

# custom-resources.yaml
calicoNetwork:
  ipPools:
  - blockSize: 26
    cidr: 192.168.0.0/16
    encapsulation: VXLANCrossSubnet
    natOutgoing: Enabled
    nodeSelector: all()
03

这页非常重要，因为后面所有现象都从这里来。Kind 的默认 CNI 明确关闭，所以在 Calico 装好以前，普通 Pod 不会拥有完整的集群网络。Pod 网段是 192.168.0.0/16，Service 网段是 10.96.0.0/16，这两组地址不要混。

Calico IPAM 的 blockSize 是 /26。它不会每创建一个 Pod 就把一条新路由广播到所有地方，而是先把一个小块分给节点，再从节点自己的块里分配 Pod IP。封装模式是 VXLANCrossSubnet。只有 Node IP 跨 underlay 子网时才封装，本实验三个 Kind 节点通常位于同一个 172.18.0.0/16 Docker 网络，所以跨节点 Pod 流量走直路由，不加 VXLAN 外层。

CNI 是同步调用

Pod 创建或删除时由容器运行时调用。成功返回前，Pod 网络还没有准备好。

Felix 持续工作

它观察期望状态并维护主机数据路径。后续策略或远端路由变化不需要重新创建 Pod。

06

这一页把容易混在一起的组件拆开。kubelet 通过容器运行时发起 CNI ADD。Calico CNI 在这个同步调用里创建 veth、写入 Pod 侧配置，并让 IPAM 分配地址。调用成功以后，容器运行时才能继续把 Pod 拉起来。

Felix 的角色不同。它长期运行在节点上，持续观察资源变化并协调 workload 接口、主机路由和策略。WorkloadEndpoint 记录 Pod IP、节点、接口和标签，IPPool 与 block affinity 则描述地址池和节点块。

地址层次也可以这样记：整个池是 /16，IPAM 按需给节点分 /26，宿主机最终为本地 Pod 安装 /32。这个层次解释了为什么地址分配既能聚合，又能精确交付。

05

现在把一次 Pod 创建放慢。API Server 收到对象以后，调度器先选节点。目标节点上的 kubelet 通过 CRI 要求容器运行时创建 Pod sandbox，运行时先准备网络命名空间，然后发起 CNI ADD。

Calico CNI 调 IPAM 拿地址，创建 veth pair，把一端放进 Pod 并命名为 eth0，另一端留在宿主机并命名为 cali 开头。随后它登记 WorkloadEndpoint，返回 IP、路由和 DNS 配置。运行时成功，kubelet 最后才把 Pod 的 Running 和 IP 状态写回 API Server。

所以 Pod 卡在 ContainerCreating 时，不要只盯镜像。CNI 二进制、CNI 配置、IPAM、节点路由和 Calico 组件都可能在这条链上。

06

进入 multitool 以后，先看 ip addr。课程示例的 Pod IP 是 192.168.146.66/32。这个 /32 很关键，它告诉我们 Pod 并没有认为旁边还有一个 192.168.146.0/26 的二层网段，它只拥有自己这个地址。

eth0@if6 里的 if6 是对端接口索引的提示。Pod 里的 eth0 和宿主机上的 cali 接口是一对 veth。MTU 1450 则来自 VXLAN 的最坏情况预留。本实验设置 VXLANCrossSubnet，同子网节点间通常不会封装，但 Pod 接口仍按可能封装的路径设置 MTU。

07

很多人第一次看到这两条路由会问：169.254.1.1 到底配在哪张网卡上？答案是 Calico 把它当作一个虚拟的链路本地下一跳。Pod 只需要知道，所有流量从 eth0 交给这个下一跳。

宿主机端并不要求 cali 接口真的拥有 169.254.1.1。Calico 让宿主机对这个下一跳表现得可达，并确保 Pod 总是拿到宿主机的 MAC。接下来真正的目的地选择发生在宿主机 Linux 路由表里。

从 Pod 回到宿主机，第一步一定要先定位 Pod 在哪台 Node 上。课程示例显示 multitool 在 pod-network-worker，IP 是 192.168.146.66。进入这台 Kind 节点以后查路由，可以看到一条精确的 /32 主机路由，出口就是 cali6d09fa47963。

12

这页可以切换两个模式。先看本实验。worker 的路由把目标 Pod 指向 worker2 的 Node IP 172.18.0.2。两个 Node IP 同属 172.18.0.0/16，所以 VXLANCrossSubnet 判断为同子网，线上传的是原始 Pod 包，源和目的仍然是两个 Pod IP。

切到跨子网模式，内层 Pod 包保持不变，Calico 再套一层 VXLAN。外层源和目的变成两个 Node IP，通过 UDP 4789 穿过不认识 Pod CIDR 的 underlay。目的节点解封装后，再用本地 /32 路由把包送进 cali 接口。

课程 Lesson 03 的示例跨节点 ping TTL 是 62，可以理解为源节点和目的节点各完成一次三层转发。这个数值是观察线索，实际环境仍要以抓包和路由为准。

先比较 Node 子网，再决定封装

VXLANCrossSubnet 的判定边界

检查项本课程环境跨 underlay 子网
Node IP172.18.0.3 → 172.18.0.2例如 10.10.1.10 → 10.10.2.10
子网关系同属 172.18.0.0/16不在同一 Node 子网
线上报文原始 Pod IP 包VXLAN 外层 Node IP + 内层 Pod IP
underlay 要求能路由 Pod 前缀或使用远端 Node 下一跳只需能路由 Node IP 与放行 UDP/4789
MTUPod MTU 仍按 1450 配置1450 为 VXLAN 头部留空间

Pod 身份保留

集群内 Pod 到 Pod 通信通常不做 SNAT，策略与抓包仍能看到真实 Pod IP。

natOutgoing 的边界

它针对发往 Calico IPPool 之外的目的地进行源地址转换，不等于集群内互访要 NAT。

路由来源要实查

用 ip route、Calico 配置和组件状态判断，避免把所有远端路由都口头归因于 BGP。

13

VXLANCrossSubnet 的判断对象是 Node IP 所在的 underlay 子网，不是两个 Pod IP 是否属于同一个 /26。Pod A 和 Pod B 一定来自不同节点块，但只要两个 Node IP 同子网，Calico 就可以省掉 VXLAN 外层。

natOutgoing 也要讲清边界。课程把它设为 Enabled，主要用于 Pod 访问 Calico 地址池之外的网络。集群内 Pod 到 Pod 通信保留源 Pod IP，这样 NetworkPolicy、日志和服务端看到的身份才准确。

至于远端 Pod block 路由由谁下发，不能只凭“Calico”两个字就说是 BGP。VXLAN IPPool 的 cluster route 可以由 Felix 编程，具体环境要看 BGPConfiguration、FelixConfiguration、IPPool 和路由协议状态。

排查网络最有效的方法，是在四个点形成证据链。第一，在 Pod 内看 eth0 和默认路由。第二，在源节点用 ip route get 看系统准备把目标 Pod 发到哪里。第三，在目的节点看本地 /32 是否落到正确 cali 接口。

最后用 tcpdump 验证报文形态。同子网直路由时，Node 链路上应看到原始 Pod 源、目的地址。跨子网 VXLAN 时，可以同时用 udp port 4789 和 inner Pod IP 作为过滤条件。抓包要配合路由表解释，单独看到一个包并不能证明整条路径正确。

把现场现象串成模型

一条数据路径的三个层次

01

Pod 边界

eth0 /32 把地址放进独立 namespace，169.254.1.1 把所有非本地流量交给宿主机。

02

Node 路由

veth 把包送进 Linux 主机协议栈，本地 Pod 使用 /32 路由，远端 Pod 使用远端节点或隧道下一跳。

03

Underlay 运输

同子网直接传原始 Pod 包，跨子网由 VXLAN 以 Node IP 运输，目的节点再交付给 cali*。

讲清这三个层次后，Pod IP、Node IP、Service IP、veth、路由和 VXLAN 就不会挤在同一个模糊的“容器网络”概念里。

18

最后收束成三个层次。Pod 边界解决地址和隔离，Node 路由解决本机交付与远端下一跳，underlay 负责把节点之间的包运过去。VXLANCrossSubnet 只改变第三层的运输方式，不改变 Pod 看到的 eth0、/32 和虚拟下一跳模型。

现场排错时也按这三层走。先确认 Pod 能把包交出来，再确认源节点知道往哪发，然后确认 underlay 或 VXLAN 能把包运到目的节点。到达目的节点以后，最后一条 /32 路由把包送进目的 Pod。
