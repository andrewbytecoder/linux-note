01Pod 网络为什么这么重要？

在 Kubernetes 里，每个 Pod 都需要一个唯一 IP 和正常连通才能干活

① Pod 太"短命"了
Pod 是 ephemeral（短暂的），一天能被创建销毁无数次。每来一个新 Pod，都得立刻能跟别的 Pod、Service、外网说话。
② 隔离，但别真断开
每个 Pod 有自己的 network namespace（网络命名空间）——这是安全隔离。但光隔离不行，还得有机制把 Pod 和宿主机的网络"桥"起来。
③ 服务发现全靠它
网络通了，Pod 才能访问 Service、做 DNS 解析、不管你跑在集群哪个角落都能找到彼此。
④ 同 Pod 内多容器
一个 Pod 里多个容器要 localhost 互访——这要求它们共享 netns，接口也得管好。
Calico 的做法：创建虚拟网卡、管 IP 分配、写路由表、打通全集群 Pod 互通——"一整套包圆了"。
口语比喻：「你可以把 Pod 想成刚交房的一套公寓。Calico 是物业：给你门牌号（IP）、拉网线（veth）、画好小区地图（路由表）、再给你个前台电话（DNS）。」

03Pod 诞生时，到底发生了什么？

10 步流水线 —— 点「下一步」逐条走，或点「自动播放」

01kube-apiserver 收到创建 Pod 的请求，把它调度到某个节点上
02kubelet 发现有新 Pod 分配给本节点，去叫容器运行时（containerd / CRI-O）
03容器运行时先把 Pod 的网络命名空间建出来（现在还是"空房间"）
04容器运行时调用 Calico CNI 插件：「喂，给这个房间接网」
05Calico CNI 向 Calico IPAM 要一个 IP。IPAM 从本节点被分配到的 IP 块里拿一个给它
06Calico CNI 创建一对 veth pair：一头留在主机叫 cali123abc，另一头进 Pod 叫 eth0
07Calico CNI 把 WorkloadEndpoint 信息（Pod IP、接口名、节点、标签）写进 Calico datastore
08Calico CNI 把网络配置结果（成功）返回给容器运行时
09容器运行时向 kubelet 报告：「网通了」
10kubelet 回写 kube-apiserver：Pod 状态 = Running，以及分到的 IP
还有两件"顺手"的事：Calico 会在主机上写到 Pod IP 的直连路由（走 Calico 接口）；同时给 Pod 配一条默认路由，下一跳是虚拟网关 169.254.1.1，用来跑集群内通信。
结果：Pod 拿到了唯一 IP，从此能借 Calico 的路由基础设施，跟全集群的 Pod 说话。

👆 点击上面带虚线下划线的字段，看它到底啥意思。
口语：「注意这个 /32——很反直觉对吧？平时咱们见 /24。Calico 故意用 /32，意思是'这个 Pod 就是一个孤零零的点'，路由全靠主机上单独一条一条写。这样每个 Pod 彼此间就是点对点链路，干净利落。」

08veth pair：一根"虚拟网线"

一头在 Pod（eth0），一头在主机（cali*）—— 点按钮看它们配对

Pod netns
eth0@if6
192.168.146.66/32
◄══►
Host netns
cali6d09fa47963@if2
无 IPv4（纯转发）
点上面的按钮，让 Pod 和主机连起来…
ip addr | grep cali6d09fa47963 -A3  (在主机上)
6: cali6d09fa47963@if2: <...> mtu 1450 ...
    link/ether ee:ee:ee:ee:ee:ee ... link-netns cni-03a82789-...
    inet6 fe80::ecee:eeff:feee:eeee/64 scope link
@if6 ↔ @if2
Pod 里的 @if6 指主机 6 号口；主机的 @if2 指 Pod 里 2 号口——互指
主机侧没 IPv4
主机这头根本不需要 IP——三层转发直接按路由走，不靠 IP

09Pod 的路由表：只有两行，但很妙

ip route —— 一个"假网关"，搞定所有出向流量

ip route (in pod)
default via 169.254.1.1 dev eth0
169.254.1.1 dev eth0 scope link
169.254.1.1 是啥？
Calico 的虚拟下一跳，是个 link-local 地址。它不是真设备，但每个 Pod 都配同一个。
为什么全用同一个？
Calico 的巧思：统一用一个下一跳 IP，路由规则就极简，不用给每个 Pod 算不同网关。
scope link
表示这个下一跳就在同一网段、直连可达，不用再绕别的网关。
Pod 怎么出去？
所有出向流量默认都从 eth0 丢给 169.254.1.1，实际就是丢给主机那头 veth。
口语比喻：「169.254.1.1 就像小区统一的'出口信箱'。不管你住哪栋，信都往这一个信箱扔，物业（主机）再从信箱取走分发。简单、统一、好维护。」

10Pod 怎么"找人"？靠 DNS

cat /etc/resolv.conf —— 点按钮看短名是怎么展开的

cat /etc/resolv.conf
search default.svc.cluster.local svc.cluster.local cluster.local ec2.internal
nameserver 10.96.0.10
options ndots:5
点上面按钮，看 kubernetes 这个短名会被解析成什么…
nameserver
10.96.0.10
CoreDNS 的 Service IP（kube-dns），所有 Pod 的 DNS 查询都发这儿
ndots:5
名字里少于 5 个点就当"相对名"，先套 search 后缀一个个试
search 后缀
帮你自动补全：default.svc. → svc. → cluster. → ec2.internal

11主机这边：一条 /32 路由"钉住"每个 Pod

先找 Pod 在哪台机，再上主机看路由

kubectl get pods -n default -o wide

Pod IP
192.168.146.66
就是 Pod 里 eth0 那个地址
dev cali6d09fa47963
去往这个 Pod 的流量，走它专属的 Calico veth 口
scope link
目标本地直连可达，压根不需要网关
关键洞察：主机上给每个 Pod 单独写一条 /32 路由，精确指向它的 cali* 口。这就是 Calico 能做到"策略精确执行 + 快速更新"的原因。

13划三个重点

① Veth 连通性
Pod 的 eth0@if6 与主机的 cali6d09fa47963@if2 配成一对，形成点到点链路。一头断了另一头立刻知道。
② 主机直连路由
每个 Pod 在主机上都有专属 /32 路由，精确指向自己的 Calico 接口，绝不"广播找人"。
③ 命名空间隔离
link-netns 这个引用告诉我们：Pod 的 netns 是隔离的，但又始终连着主机——隔离与连通兼得。
口语总结：「记住三件事就够了：一对 veth 牵手、一条 /32 路由定位、一个 netns 隔离。Calico 的 Pod 网络，本质上就是这三板斧。」

14今天我们学了啥？

① Pod 网络命名空间
每个 Pod 跑在自己的 netns 里，有专属 eth0，从 Calico IPAM 拿到唯一的 /32 IP
② Veth Pairs
Calico 给每个 Pod 建一对 veth：一头 eth0 在 Pod，另一头 cali* 在主机，组成点对点链路
③ 虚拟下一跳 169.254.1.1
Pod 所有出向流量都走这个 link-local 虚拟网关。所有 Pod 统一用它，路由大大简化
④ 主机路由表
节点为每个 Pod 维护一条 /32 主机路由，把去往该 Pod IP 的流量指向对应的 Calico 接口
⑤ DNS 走 CoreDNS
Pod 用 CoreDNS (10.96.0.10) 做全部名字解析，配合 search 域，短名也能解析
最终画面：Pod 有唯一 IP + 独立 netns + 一根 veth 连主机 + 统一虚拟网关 + 主机上一条 /32 路由 + CoreDNS 找人 = 全集群自由通信。
