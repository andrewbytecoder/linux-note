大家好，这一节我们给 Pod 的网络带宽装一个限速器。实验用 iperf3 做前后对照，没有 QoS 时能跑到每秒几个 Gbit，加上 10M 注解后，持续吞吐稳定在每秒大约 10 Mbit。

我们不会只看最后一个数字，还会解释 ingress、egress 的方向，token bucket 为什么允许首秒突发，以及 Linux tc 在 Pod 接口附近怎样执行限制。

The noisy neighbor problem

一个 Pod 可以占满共享链路

Pod Alarge transfer
Pod BAPI request
Pod Cmetrics
共享 NIC / underlay容量有限
公平性大流量工作负载挤压其他租户
时延队列增长让短请求等待
成本出口或跨区带宽不可控
SLA不同服务等级难以执行
02

多租户节点上的链路是共享资源。一个 Pod 持续大流量传输，会让同节点其他 Pod 的短请求进入更长队列，形成 noisy neighbor。

Calico QoS 在每个工作负载接口附近限制最大使用量。它解决的是上限和隔离，不是凭空增加网络容量。

03

Kubernetes 里还有一个同名概念叫 QoS Class，它由 CPU 和内存的 requests、limits 决定。这个分类影响调度和驱逐，不会限制网络吞吐。

本课的 Calico Network QoS 通过 Pod annotation 配置，执行位置在网络数据面。演讲时一定先把这两个概念分开。

Why cap network usage

带宽限制解决的四类问题

01

资源公平

限制单个 Pod 的最大速率，避免它长期独占共享链路。

02

成本控制

对备份、批处理或开发环境设置更低的出口上限。

03

性能隔离

给关键服务留下可用容量，降低突发大流量的干扰。

04

租户等级

不同租户或应用层级使用不同速率策略。

边界：限速是最大值约束，不等于保证最小带宽。物理链路拥塞时，配置 10M 也不承诺一定能达到 10M。

04

限速最直接的价值是公平，防止一个任务把链路打满。它也常用于成本控制和租户套餐。

但要准确表述：这里配置的是最大平均速率，不是带宽预留。底层链路只有 5M 可用时，Pod 不会因为 annotation 就获得 10M。

Rate, tokens and burst

Token Bucket Filter 的三个量

补充速率10 Mbit/s
tokens最大容量决定 burst
每个包消耗 token有 token：发送无 token：排队或丢弃
长期平均速率≤ configured rate
瞬时突发≤ available tokens
队列效果平滑发送或触发 drop
22

可以把 token 理解成发送许可。系统按配置速率补 token，每个包发送时消耗对应数量。

桶里预先有 token，就允许短时间跑得比 10M 快。桶空以后只能按 token 补充速度继续发送，长期平均速率被限制。

首秒高带宽是 token bucket 的正常行为。它允许短突发，适合网页小对象和短请求快速完成。

判断限速是否生效要看 burst 之后的稳定区间。课程中从第二秒开始连续四个区间都在 10.5 Mbit/s。

课程建议把测试时间改成 30 秒。第一秒 burst 仍然存在，但它在总时长中的占比从五分之一降到约三十分之一。

生产评估不要只跑一次。保持路径和并发一致，重复多轮并看稳定区间和分位数。
