大家好，这一节我们在上一课 Pod 接入主机的基础上继续往前走。现在不只看一个 Pod 的 eth0，而是让两个 Pod 真正互相发包，再用路由表、TTL 和抓包把路径一段一段证实。

实验环境完全沿用 Lesson 03。ContainerLab 创建三节点 Kind，Calico 使用 192.168.0.0/16 地址池和 /26 节点 block，两个 DaemonSet 会在每台节点各放一个 Pod，所以一共有六个测试端点。

主课程：https://k8snetworking.com/lessons/03-pod-routing

从现象到数据路径

本课回答的四个问题

01

同节点怎么走

两个 Pod 各在独立 namespace，包为什么仍要进入宿主机路由。

02

跨节点怎么走

源节点如何用远端 /26 block 找到目的 Node，再完成最终 /32 交付。

03

地址有没有变化

tcpdump 能否看到原始 Pod 源地址，路由输出里的 src 又代表什么。

04

怎样证明路径

把 ip route、TTL、Node IP 连通和目的 Pod 抓包拼成证据链。

讲解顺序固定为：先记录动态地址，再发流量，随后查源节点路由，最后在目的端抓包。

02

这节课有四个问题。同一台节点上，两个 Pod 为什么还要经过宿主机。跨节点时，源节点怎么知道目标 Pod 在 worker2。报文穿过节点以后，Pod 源地址有没有被换掉。最后，我们用哪些命令证明自己的判断。

整个实验不要从背结论开始。先用 kubectl get pods -o wide 记录本次运行的 Pod 名称、地址和节点，然后所有命令都使用这组现场值。课程示例里的 Pod 名称和 IP 会随着重建变化。

03

这套配置和上一课相同。Kind 自带 CNI 被关闭，Pod 地址池是 192.168.0.0/16，Calico IPAM 按 /26 分配节点 block。Service 网段 10.96.0.0/16 不参与我们今天的 Pod 直连 ping。

封装模式是 VXLANCrossSubnet。课程里的三个 Node IP 都在 172.18.0.0/16，因此本实验跨节点流量不需要 VXLAN 外层。源节点直接把原始 Pod IP 包交给远端 Node IP。跨 underlay 子网时才会封装，这个边界后面单独演示。

为什么用 DaemonSet

每台可调度节点都放一个副本。清单额外容忍 control-plane taint，所以控制节点也会运行。

为什么需要两套

同一节点上同时存在两个不同 Pod，才能验证 host FIB 的本地 /32 转发。

06

两个 DaemonSet 是这节课的关键设计。multitool-1 和 multitool-2 都容忍 control-plane 的 NoSchedule taint，因此三个节点各运行两个 Pod，总共六个。

Calico IPAM 把大地址池切成较小的 block。课程示例里 worker 的两个 Pod 都落在 192.168.93.192/26，worker2 的两个 Pod都落在 192.168.112.192/26。

09

同节点和跨节点的第一步完全相同。源 Pod 都把包交给 169.254.1.1，veth 把包送进源节点 Linux 协议栈。真正的分界发生在源节点查路由时。

如果查到目的 Pod 的本地 /32，包直接从另一个 cali 接口出去。如果查到远端 /26，包先交给目的 Node IP。到达远端以后，仍然由那台节点的本地 /32 完成最后一跳。

源 Pod 把 echo request 交给虚拟下一跳，包穿过 veth 进入 worker 的 Host namespace。主机路由表命中 192.168.93.202 的 /32，出口是目的 Pod 对应的 cali 接口。

TTL 是旁证。最终路径仍应结合 Host 路由表和抓包判断，因为应用或操作系统可能使用不同初始 TTL。

12

课程把 ttl=63 作为一次主机路由的证据。假设发送端初始 TTL 是 64，Host FIB 每做一次三层转发就减 1，目的 Pod 收到时就是 63。

需要把这句话讲严谨。TTL 能帮助判断跳数，但不同系统或应用可能使用不同初始值，所以它不是唯一证据。路由表命中和目的端 tcpdump 才能把路径坐实。

pod-routing-worker

目的 Pod 的本地 /32 路由

worker:/# ip route | grep 192.168.93.202

192.168.93.202 dev cali3174bc812f3 scope link

最长前缀匹配

目的地址精确命中 /32，因此优先于更宽的节点 block 或默认路由。

dev cali*

出口是 host-side veth。它的对端位于目的 Pod namespace，并在 Pod 内命名为 eth0。

scope link

内核把目的端看作该接口直接可达，不需要额外网关。

13

进入 worker 后查目的地址，可以看到一条精确 /32。Linux 做最长前缀匹配，因此这条路由直接把包送入 cali3174bc812f3。

scope link 表示目标通过这个接口直接可达。host-side veth 不需要配置目的 Pod 网段地址，它只要作为点到点出口存在，Calico 再维护邻居和策略状态。

一个常见误读

route get 的 src 不代表 SNAT

主机自己发包时

ip route get 192.168.112.197
...
src 172.18.0.2

这表示如果进程运行在 Host namespace，内核会选择 172.18.0.2 作为源地址。

转发 Pod 数据包时

inner packet
src 192.168.93.201
dst 192.168.112.197

主机转发已有报文，Pod 源地址保持不变。目的 Pod 抓包可以直接验证。

判断 NAT 看报文或 NAT 规则：不要只看 ip route get 的 src 字段。

19

这条 route get 输出最容易被误读。src 172.18.0.2 描述的是 Host namespace 自己新建一个连接时会选哪个源地址。它不表示经过这台主机的 Pod 包一定会被改写。

实际转发时，原始报文已经带着源 192.168.93.201。课程最后在目的 Pod 抓到的也是这个地址，因此集群内路径没有发生 SNAT。判断 NAT 要看真实报文和 NAT 规则。

不出现 VXLAN 外层，Node underlay 必须能承载到远端节点的转发。

跨子网路径

underlay 只需认识 Node IP，同时允许 UDP/4789 和匹配路径 MTU。

21

VXLANCrossSubnet 比较的是两个 Node IP 的 underlay 子网。课程里 .2 和 .3 同属 172.18.0.0/16，所以不封装，线上能直接看到原始 Pod 源和目的地址。

如果两个 Node IP 位于不同子网，Calico 会把内层 Pod 包放进 VXLAN 外层。外层源、目的变成 Node IP，通过 UDP 4789 运输。目的节点解封装后，继续按本地 /32 交付。

23

跨节点路由分两级收敛。源节点只负责把远端 /26 送到正确节点。到达 worker2 后，worker2 自己维护的 /32 再把包送进 cali2add6b13a99。

这正是聚合和精确交付的分工。远端节点不需要知道每个 cali 接口，本地节点才掌握 Pod 与 veth 的一一对应关系。

同一条流量放在不同接口抓，会看到不同层次。源 Pod eth0 能证明应用发出了什么。源 Node 的 cali 接口证明报文进入主机。Node eth0 或 vxlan.calico 用于判断节点间运输方式。目的 Pod eth0 最终验证端到端身份。

路由表和抓包解决不同问题。ip route 说明内核选择，tcpdump 说明真实报文。排错时至少要把这两类证据配对。

按症状定位

同节点不通查 veth、本地 /32、NetworkPolicy
同节点通，跨节点不通查 Node IP、远端 /26、rp_filter
跨子网才失败查 UDP/4789、vxlan.calico、MTU
目的端源地址异常查 NAT 规则与测试目标是否在 IPPool 外

27

现场演示建议先用 Pod 列表固定变量，再分别做同节点和跨节点 ping。每次都让观众看到对应的 Host 路由，最后用目的 Pod 抓包收尾。这样不是只展示“ping 通了”，而是展示为什么能通。

Summary and sources

一条跨节点路径的完整证据链

01

Pod 交给 Host

Pod 使用 /32 和 169.254.1.1。veth 把原始 IP 包送进源节点。

02

节点按 block 路由

同节点命中本地 /32。跨节点命中远端 /26，并以目的 Node IP 为下一跳。

03

目的端精确交付

目的节点用本地 /32 送入 cali*。tcpdump 证明 Pod 源地址保持不变。

最后把整条路径压缩成三句话。Pod 只知道自己的 /32 和统一虚拟下一跳。源节点根据目的地址选择本地 /32 或远端 /26。目的节点再用本地 /32 完成最后交付。

TTL 给出跳数线索，ip route 给出转发决策，tcpdump 给出真实报文。三类证据一致时，我们才算真正解释清楚 Calico Pod Routing。

课程示例地址、Pod 后缀和 cali 接口名都是动态值。现场演示必须以本地环境输出为准。本课使用 Calico 3.30.0，官方链接指向当前文档，版本敏感项应再对照 3.30 文档。
