## k8s network

### kubernetes network implementations
k8s内置的网络功能模块kubenet仅仅能提供一些基本的网络连接功能，不过最常见的是通过使用第三方网络解决方案，这些解决方案可以通过CNI(容器网络接口)API与k8s进行集成。
常见的CNI插件有两种
- 网络插件，负责将Pod连接到网络中
- IPAM(IP地址管理)插件，负责分配pod的ip地址


### k8s services
k8s服务提供了一种将一组pod的访问进行抽象化的方式，使其表现为一种网络服务。在集群内部，这种网络服务通常表现为一个虚拟IP地址，而kube-proxy则负责将连接分配到支持该服务的哪些Pod上。
该虚拟IP可以通过k8s的DNS进行查询和获取。无论支持该服务的Pod是否会被创建或销毁，以及支持该服务的Pod数量是否会随着时间变化，DNS名称和虚拟IP地址都保持不变。
这种对短暂存在的容器进行稳定管理的服务抽象机制，正是给予k8s构建的容器服务平台的基石。

Kubernetes 服务还可以定义如何从集群外部访问该服务，可以使用以下其中一种方式：
- 一个节点端口，可以通过每个节点上的特定端口来访问服务
- 负载均衡器是一种网络组件，它提供一个虚拟的IP地址，使得服务可以从集群外部进行访问。
- 除了节点端口和负载均衡器之外，k8s ingress还提供了HTTP和HTTPS路由规则，使得服务可以对外暴露，从而让集群外的客户端能够访问这些服务。

> 在本地部署环境中使用calico，还可以生命服务的ip地址，这样就能够方便地访问服务，而无需通过节点端口或者负载均衡器进行转发。

### NAT outgoing 
k8s网络模型规定，容器之间必须能够直接使用容器自身的ip地址进行通信，不过并没有要求容器的IP地址能够跨越集群边界进行路由。许多k8s网络实现方式采用的时overlay网络。在这种模式下，当容器尝试与集群外的ip地址建立连接时，承载该容器的节点会使用SNAT技术，将数据包的源地址从容器的IP转化为节点IP。这样连接就可以被路由到目的地(因为节点IP是可以被路由的)。而返回的数据包则会被节点自动重新映射，将节点IP替换为容器IP，然后再将其转发会容器。 

想要详细了解可以参考[egress](https://docs.tigera.io/calico/latest/about/kubernetes-training/about-kubernetes-egress)

在使用calico时，根据具体环境，你可以选择是否使用overlay网络，或者使用可以完全进行路由的Pod IP地址。如果需要更高的灵活性，Calico还允许为你指定的IP地址范围配置出站NAT设置。




## kubernetes ingress是什么
kubernetes ingress是一种API对象，用于管理队kubernetes汲取内服务的外部访问，通常是HTTP和HTTPS进行访问。用户可以通过该对象定义和配置应用程序的负载均衡、SSL termination以及基于name-base的虚拟主机服务。通过与现有的网络基础设施继承，kubernetes ingress能够确保用户能够一致且安全的访问应用程序。

与独立管理服务不同，ingress提供了易总统一的解决方案来处理多个服务，从而简化了路由规则的管理工作。ingress充当了入口点，可以从一个集中化的资源点管理和执行路由决策、SSL配置以及流量分配的操作。这样就能避免手动配置多个外部接入点的繁琐工作。

很多团队并不是"自己从零搭建 K8s 集群 + 自己管网络"，而是：

- 通过 **CaaS（Container as a Service）平台**​ 来使用 K8s
- Ingress 和负载均衡由平台**作为托管能力提供**
- 团队只需要关心"我的应用怎么暴露出去"，不需要关心底层怎么实现

### What is a kubernetes Ingress Controller?
kubernetes ingress controller负责执行入口规则，它根据指定的入口配置，将外部的请求路由到kubernetes集群中的服务实例，该控制器是一个守护进程，它负责利用这些规则来决定如何负载均衡、路由处理以及管理流量。
目前有几种可用的入口控制器，每种控制器都具备不同的功能和性能特点。常见的选择包括 NGINX、HAProxy 和 Traefik。这些控制器通常提供诸如自定义指标统计、额外的安全控制等功能，而不仅仅是基本的入口管理功能。

### kubernetes ingress vs kubernetes egress
在管理网络流量方面，kubernetes的入口和出口功能发挥着不同的作用
ingress负责处理进来的连接请求，并将外部请求路由到集群内的相关服务。其核心目标是确保应用程序的访问安全并对其进行管理。
egress负责管理从集群内部到外部的服务的出站连接，从而控制各个Pod队外部系统的访问权限。出口组件对于集群内服务之间及进行通信至关重要。控制出口流量是确保安全的关键，因为只有经过授权的通信才能与外部系统进行交换。

### kubernetes ingress 与 kubernetes API gateway的区别
kuberneetes API gateway 的推出旨在解决kubernetes ingress功能的局限性问题，它通过提供一种标准化的流量管理模型，使得不同入口控制器能够协同工作。与仅专注HTTP流量的ignress不同，API gateway引入了更多用于复杂流量控制和灵活配置的资源对象。
同时支持L4和L7协议，为Kubernetes环境中的网络流量管理提供了更加全面的解决方案，通过诸如GatewayClass、Gateway和HTTPTRoute等新的资源对象，Gateway API能够实现更高级的路由管理和流量管理功能，并提高在不同控制器实现中的可移植性。

**Kubernetes Ingress 与 Gateway API 之间的主要区别：**
- 协议支持：Ingress 仅支持 L7 协议，如 HTTP 和 HTTPS；对于非 L7 协议，则需要使用自定义扩展来实现支持。而 API Gateway 则同时支持 L4 协议（例如 TCP、UDP）和 L7 协议。
- 可移植性：Ingress 定义因供应商而异，具有独特的语法和特性。Gateway API 能够在所有符合标准的控制器之间建立统一的标准，从而减少了对自定义配置的需求，使得迁移变得更加容易。
- 流量管理：Ingress 内置的流量管理功能有限，因此需要通过扩展来实现诸如请求镜像或 A/B 测试等功能。API Gateway 提供了对这些高级功能的支持，并且能够提供细粒度的指标数据。
- 资源对象定义：Ingress 不会引入新的资源对象，而 Gateway API 则会引入多个新的对象，包括 GatewayClass、Gateway 和 HTTPRoute 等。这些新对象使得对流量规则和功能的控制更加精细。
- 路由定制：入口路由仅限于基于路径或主机的路由方式。API Gateway 能够根据各种因素进行路由定制，包括任意头部字段、路径以及主机信息等。
- 可扩展性：在 Ingress 中增强诸如身份验证或速率限制等功能通常需要使用特定的注释。而在 API 网关中，这些功能已经内置在规范中，从而提供了更简单的扩展功能的方式。

## 在kubernetes中,DNS是如何工作的？
DNS是Kubernetes中的一个组件，它实现了服务发现以及不同Pod之间的通信，当集群中创建一个Pod或服务时,kubernetes胡自动为这些对象生成DNS记录。这样，像`service.namespace.svc.cluster.local` 这样的人类可读的域名就可以被转化为机器能识别的IP地址。

这些记录遵循特定的命名规范，由集群内部运行的DNS服务进行维护，通常使用CoreDNS服务，这个DNS服务确保每个Pod和服务都能够通过唯一且可解析的DNS域名进行访问，从而简化集群内的通信和集成工作。

当一个Pod发起DNS查询时，请求会被发送到集群内的CoreDNS服务器。CoreDNS会检查其数据库中的记录以解析该查询。如果DNS查询涉及内部服务或Pod，CoreDNS会返回相应的IP地址，对于外部的DNS查询，CoreDNS可以将请求转发给外部的DNS服务器进行处理。

### 在k8s中，哪些对象会获得DNS记录？
*Pods*
在k8s中，每个拥有配置正确的DNS策略的pod都能有自己的DNS记录，Pod的DNS名称通常为 `pod-ip-address.namespace.pod.cluster.local` ，这种结构确保了每个Pod都能通过DNS被唯一标识，并在集群内部被正确访问。Pod的DNS记录有助于实现Pod和服务之间的网络通信，无论这些节点位于同一个节点上，还是分布在集群中的不同节点上。这一点对于保持依赖节点间通信的应用程序的功能至关重要。

*Services*
k8s中服务也会被记录DNS记录，这些记录使得其他服务或容器能够通过易于记忆的域名来定位这些服务，一个典型的DNS记录可能看起来像 `service.namespace.svc.cluster.local`。 这里的`service` 指的是k8s服务的名称，它提供了一个统一的端点，以便访问由该服务管理的容器。
为每个服务配置独立的DNS，可以解决Pod IP会动态变更的问题。这样即使集群中创建、销毁或者移动Pod时，系统也能保证持续的连接和可用性。

### What is dnsPolicy in k8s
dnsPolicy是Pod配置中的一个规范，他规定了在Pod的容器中如何解析DNS请求。这在k8s集群中的网络通信中起着至关重要的作用，因为它决定了由哪个DNS服务来相应来自Pod的DNS请求。这一配置影响了服务和Pod在k8s集群内部和外部通过DNS进行相互查找的方式。
dnsPolicy设置提供了集中预定义的选项，每个选项都以不同的方式来操控DNS解析过程。

以下是一个ClusterFirst的DNS策略的容器清单示例：
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: busybox
  namespace: default
spec:
  containers:
  - image: busybox:1.28
    command:
      - sleep
      - "3600"
    imagePullPolicy: IfNotPresent
    name: busybox
  restartPolicy: Always
  dnsPolicy: ClusterFirst
```

### Values in dnsPolicy 
*Default*
默认的 dnsPolicy 策略会使用由运行该容器的节点所继承的 DNS 配置。这种策略非常简单，因为它依赖于宿主机的现有 DNS 设置，因此不需要在 Kubernetes 中进行任何特殊的配置。如果节点的 DNS 配置发生变化，那么容器中的 DNS 配置也会自动更新。
然而，虽然 Default 模式较为简单，不会将 DNS 服务隔离在集群内部，但在节点配置不同或需要将服务从一种集群环境迁移到另一种环境时，这种方式可能会引入复杂性。

*None*
当 dnsPolicy 被设置为 None 时，用户就可以完全控制 DNS 设置。如果使用此策略，用户必须明确指定 DNS 查询的解析方式，这可以通过提供 DNSConfig 来实现。这种设置适用于需要自定义 DNS 配置的场景，比如混合云环境或具有特殊网络架构的情况。None 策略特别适用于微调 DNS 配置，以优化性能或满足特定的安全需求。不过，需要仔细配置以确保 DNS 解析能够在集群中的所有节点和容器上正常运作。

*ClusterFirst*
ClusterFirst dnsPolicy 使得容器可以忽略宿主机的 DNS 设置，而只使用 Kubernetes 集群中指定的 DNS 服务器进行域名和服务的解析。这样就能确保集群内的域名和服务的 DNS 查询始终在集群内部进行解析。这通常是大多数 Kubernetes 部署的默认设置，能够提升内部连通性和安全性。
该政策旨在防止 DNS 查询被用于无法访问的集群内部资源。这样可以避免将集群内部的 DNS 查询泄露到外部 DNS 服务器上，从而保护集群的内部结构。

*ClusterFirstWithHostNet  使用主机网络进行集群划分*
对于启用了 hostNetwork 设置的 Pod 来说，应该使用 ClusterFirstWithHostNet dnsPolicy 策略。这一策略允许 Pod 使用主机的网络资源，同时优先处理内部集群的 DNS 解析，而不是查询外部 DNS 服务器，就像 ClusterFirst 策略一样。
该政策对于需要同时访问集群服务与外部网络的应用程序来说至关重要。它能够实现内部集群隔离与必要外部访问之间的最佳平衡，从而确保主机网络上的容器能够进行高效且安全的通信。

### 在k8s中实现DNS策略的最佳实践
#### Fine-Tune CoreDNS 优化CoreDNS的功能
对CoreDNS进行精细调优对于提升k8s集群中DNS性能和可靠性至关重要。CoreDNS具有极高的可配置性，你可以调整各种参数以满足环境的特定需求。例如，通过自定义缓存设置，你可以决定DNS存储的时间长度，而这直接影响重复查询DNS的解析速度。
此外，还可以启用查询日志功能，这有助于审计和排查DNS相关问题，从而了解DNS在集群中的使用情况。调整CoreDNS还需要配置其他插件，例如使用forward插件来高效处理外部DNS查询，或使用rewrite插件来动态管理DNS请求。

### 限制外部DNS查询
在k8s集群内部限制外部DNS查询时一种提高安全性和效率的最佳实践。k8s中通常包含一些敏感的服务，这些服务在绝对必要的情况下才能与外部进行通信。
通过CoreDNS来限制哪些域名可以被外部解析，你可以防止内部服务和数据意外泄露到互联网上，从而降低例如DNS欺骗或数据窃取攻击等风险。这种限制可以使用CoreDNS插件来实现，例如k8s插件可以确保内部服务的DNS查询在集群内部进行处理，而Block插件则能够明确阻止对某些域名的查询。

### 使能DNS缓存功能
在k8s中启用DNS缓存时提升DNS操作性能和效率的强大方式。当启用DNS缓存后，COreDNS会在一定时间内存储响应结果，这样对于同一域名的重复查询就可以更快地得到响应，而无需反复的访问原始数据，这减少了延迟，使得服务发现更加迅速，同时减轻了DNS服务器的负担，在大型集群中DNS查询可能成为性能瓶颈，因此这种优化方式尤其有意义。

### 实现DNS负载均衡功能
在k8s环境中实施DNS负载均衡功能可以确保DNS查询能够均匀分布在多个DNS服务器上，从而避免任何一台服务器过载，进而提高DNS基础设施的弹性。CoreDNS可以配置多种负载均衡策略，例如 `round_robin`，这些策略通过在不同端点之间切换DNS响应来处理负载。
这不仅提升了DNS服务的可用性，还能确保在高峰流量期间，查询也能得到高效的处理。在大型的生成k8s环境中，负载均衡尤为重要。

## 在k8s中DNS是如何工作的
k8s会自动管理所有服务的DNS记录，从而实现内置的服务发现功能。无需不断变化的IP地址，集群中的容器可以通过稳定的、易于理解的域名与任何服务进行通信。CoreDNS是集群默认的DNS服务器，它会监控k8s的API，并在服务与容器发生变动的时候保持这些DNS记录的一致性。

在 Kubernetes 中，域名系统（DNS）被用于实现集群内的名称解析功能。它可以将服务名称转换为 IP 地址，从而使应用程序能够进行通信。在 Kubernetes 中，DNS 被集成以自动为各种集群服务提供 DNS 名称，这样一来，用户就可以使用更易于记忆的名称来访问这些服务，而不需要记住复杂的 IP 地址。

### 按照服务类型划分DNS记录类型
- 标准服务(Standard Services)：将地址映射到一个单一的A(IPv4)或AAAA(IPv6)记录上，该记录指向服务稳定的ClusterIP地址。
- 无头服务(Headless Services)：这种服务类型的特点是使用cluterIP参数进行定义，其地址直接指向所有后端节点IP的A/AAAA记录，直接指向pod地址
- 外部名称服务(ExternalName Services)：通过CNAME记录将内部名称映射到外部域名，且无需使用ClusterIP
- SRV records：用于识别某个服务中定义的命名TCP或UDP端口

### k8s中DNS系统如何在幕后运作
- 默认服务器： CoreDNS是默认的集群DNS提供商，它以Pod的形式运行，这些Pod被命名为kube-dns的servcie在kube-system命名空间中暴露出来。
- API tracking: CoreDNS会持续监控k8s API，以便及时发现新的、已修改或删除的服务和端点
- Dynamic updates: 动态更新，系统会不断地更新记录，使得每个DNS名称都能实时映射正确的ClusterIP或Pod IP地址


### 默认域名 `cluster.local`
在 Kubernetes 集群中，默认域名是 `cluster.local` 。这个域名会被自动添加到任何不包含完全限定域名的服务或容器名称中。使用默认域名可以简化内部 DNS 解析工作，因为整个集群都遵循统一的命名规范。例如，如果你只使用一个服务名称而不指定域名，Kubernetes 会默认在 `cluster.local` 域名范围内进行解析。

这种默认的域名配置方式确保了服务与 Pod 能够相互通信，而无需引用它们完整的 DNS 名称。这样一来，集群内的服务发现过程变得更加简洁。此外，这种方法还能避免与外部 DNS 名称产生冲突，因为 `cluster.local` 这个域名仅用于 Kubernetes 集群内部的通信用途。

### Services的DNS名称
在 Kubernetes 集群中，每个服务都会自动被分配一个完整的域名，这样其他工作负载就可以通过内置的服务发现机制来访问该服务。在 Kubernetes 中，服务会被分配一个 DNS 名称，这使得在集群内部可以轻松访问这些服务。服务的 DNS 名称格式为 `<service-name>.<namespace>.svc.cluster.local` 。
- service-name: k8s中service名称
- namespace：服务所在命名空间
- svc：service资源的标准后缀
- cluster.local: k8s集群的默认后缀


### Pod的DNS名称
在 Kubernetes 中，Pod 也可以通过 DNS 进行访问，不过这种方式通常不如直接访问服务那样常用。在一个有状态的集群中，或者当使用了特定的 `hostname` 和 `subdomain` 时，每个 Pod 都可以拥有一个 DNS 名称，该名称的格式为 `<pod-name>.<headless-service-name>.<namespace>.svc.cluster.local` 。
- pod-name: pod的名称
- headless-service-name: 需要一个无集群 IP 的服务，即没有集群 IP 地址的服务。这种服务负责实现针对单个容器的 DNS 名称的解析。该服务的作用是让容器能够基于 DNS 进行服务发现。

## What is container as a service(CaaS)?
容器即服务（CaaS）是一种云服务模型，它使得开发者和 IT 团队能够通过基于容器的虚拟化方式管理和部署容器、应用程序以及集群。该服务为用户在云环境中构建、发布和运行容器化应用程序提供了框架，从而简化了部署过程。


### CaaS vs. PaaS
PaaS 将大部分基础设施和中间件管理的任务抽象出来，让开发者无需直接处理底层服务器或网络问题，就可以开发、运行和管理应用程序。PaaS 通常对支持的技术和语言有更明确的规定，但通过提供集成开发环境、数据库以及中间件等组件，能够显著加快开发速度。
CaaS 提供了更精细的控制能力，让开发者能够在高度可扩展的环境中管理容器化应用程序。它在容器内部使用的技术栈方面具有灵活性，因此非常适合微服务架构，因为不同的组件可能有着各自不同的需求。

### CaaS vs. IaaS
IaaS 提供了对基础设施以及应用程序部署方式的最大的控制能力，用户可以通过互联网访问虚拟化的计算资源。它允许用户按使用量付费来租用虚拟机、存储和网络资源，但用户需要自行管理操作系统、中间件、运行时环境以及应用程序层。这种模式非常适合那些希望在构建环境时保持灵活性，同时又能控制自己基础设施的组织。
CaaS 通过将容器编排作为服务来提供，从而大大简化了基础设施管理的工作。用户无需管理虚拟机或网络配置，只需专注于容器的部署和管理。这简化了开发者的操作流程，使他们能够在不担心底层硬件或虚拟机管理问题的情况下部署应用程序。

### CaaS vs. SaaS
SaaS 模式是通过互联网来交付软件应用的方式，用户无需担心安装、维护或基础设施方面的问题，就可以使用这些软件。SaaS 解决方案完全由服务提供商来管理。用户通常通过网页浏览器与软件进行交互，并支付订阅费用以获取软件服务。这种模式非常适合那些需要全套软件解决方案的用户，因为他们不需要管理硬件或软件更新。
CaaS 为部署和管理容器化应用程序提供了环境支持，它专注于应用程序的基础设施和运营方面。它让开发者和 IT 团队能够控制部署过程、扩展能力以及容器的管理流程，同时消除了许多与基础设施相关的复杂性。


## k8s中的Egress Gateways 
Kubernetes 中的出口网关是负责管理集群向外部系统传输数据的网络组件。它们能够执行安全策略，并控制访问权限，确保数据仅被发送到授权的目标地址。出口网关提供了一个集中的监控和管控点，从而提升了网络安全和合规性。
出口控制是 Kubernetes 安全策略中的一个层次结构，该策略还包括工作负载隔离、策略执行以及流量监控等内容。
外出网关通过将出站流量的处理整合为可管理且可监控的单元，从而简化了合规性审计和安全监控工作。这一布局还有助于防止数据泄露和未经授权的数据访问，从而有效控制集群内服务与外部资源之间的交互方式。

### Egress Gateways 使用场景
1. 与外部防火墙集成
在将 Kubernetes 服务与外部防火墙集成时，Egress gateways尤其有用。它们能够通过控制方式将所有出站的流量引导到指定的路径上，从而实现集群与外部安全系统之间的无缝通信。这种设置能够提升安全性，因为只有经过授权的连接才能通过防火墙，从而确保 Kubernetes 部署符合现有的安全协议要求。
此外，出口网关可以配置为处理动态 IP 地址和服务端点，这使得维护防火墙规则变得更加容易。这种灵活性使得在每次服务更新或扩展时，无需手动重新配置防火墙规则，从而确保操作的安全性和效率。

## 什么是k8s调试
Kubernetes 调试是指诊断和解决 Kubernetes 集群中各种问题的过程。这包括探究为什么 Pod 无法启动、服务无法连接、基础设施出现不可预测的行为，以及应用程序是否按预期运行等问题。Kubernetes 的调试与传统调试方式不同，因为它涉及的是一个由大量动态组件构成的分布式系统，需要进行复杂的协调操作。

在 Kubernetes 中进行调试时，通常会面对多层抽象结构。有应用程序层，即运行在容器上的应用；还有 Kubernetes 对象，如 Pod 和服务；此外还有底层的基础设施，比如节点和网络；最后还有 Kubernetes 的控制层。每一层都可能带来相应的挑战，因此调试工作是一项复杂的任务，需要扎实的 Kubernetes 架构和概念理解。

### 为什么k8s调试很重要
- 确保系统的可用性和可靠性：在 Kubernetes 环境中，应用程序需要能够自我修复并按需进行扩展。然而，当出现问题时，比如某个服务无法响应或某个容器崩溃，那么拥有相应的技能和工具来恢复功能并确保系统正常运行是非常重要的。
- 性能优化：经过良好调度的 Kubernetes 集群能够高效运行，有效利用资源，为应用程序提供最佳的性能表现。调试过程可以帮助我们发现可以提升性能的地方，无论是优化资源分配还是简化执行路径。
- 识别配置错误或漏洞：Kubernetes 环境中存在的配置错误可能导致敏感数据暴露、未经授权的访问，或者部署流程出现故障。在这些错误造成危害之前，进行调试工作是非常重要的。
- 预防未来的问题：Kubernetes 调试不仅仅是一项反应性任务，还是一项预防性工作。通过定期对系统进行审计，并采用 Kubernetes 调试技术，你可以避免问题发生。

### 调试k8s中常见的问题
#### CrashLoopBackOff

*Understanding CrashLoopBackOff*
当遇到 `CrashLoopBackOff` 错误时，意味着你的 Kubernetes 容器在启动过程中会反复出现崩溃的情况，而 Kubernetes 试图重新启动该容器，但每次都会失败。这种崩溃和重启的循环可能是由多种问题引起的，从配置错误到更严重的应用程序问题都有可能。

*Identifying the cause*
要确定原因，首先查看失败容器的日志。可以使用 `kubectl logs <pod-name>` 来进行操作。寻找其中的错误信息或堆栈跟踪信息，这些信息可以帮助了解发生了什么问题。如果日志提供的信息不够充分，可以使用 `kubectl describe pod <pod-name>` 来获取有关容器事件和状态的更多细节。

*Resolving the Issue*
一旦确定了问题的原因，解决该问题可能需要修改配置文件、调整资源限制，或者处理与应用程序相关的错误。如果问题是由于配置问题导致的，你可能需要编辑相关的部署或容器规格设置。而对于应用程序本身的错误，则可能需要调试应用程序的代码。

#### Service Connectiovity issues
*Troubleshooting service connectiovity*
在 Kubernetes 中，服务连接问题可能源于服务定义配置错误、网络策略设置不当或 DNS 问题。为了解决这个问题，请首先确认服务和服务实例都已正确定义并正常运行，可以使用 `kubectl get services` 和 `kubectl get pods` 来进行验证。

*investigating network policies*
如果您的定义是正确的，那么下一步就是检查现有的网络策略。这些策略可能会限制容器之间的通信，因此请确保这些策略被配置为允许必要的连接。通常，可以通过如 Calico 这样的 CNI 插件来实现这一点。当外出连接出现故障时，还需要检查 Kubernetes 的出口配置情况，因为离开集群的流量是单独进行控制的

*Resolving DNS issues*
DNS 问题也是导致连接问题的一个常见原因。请确保您的 DNS 设置已正确配置，并且您的容器能够解析服务名称。您可以在容器内使用 `kubectl exec <pod-name> -- nslookup <service-name>` 来测试 DNS 解析功能。

####  PVCs Stuck in Pending state

*Understanding PVCs*
持久卷声明（Persistent Volume Claims, PVCs）是 Kubernetes 中用于请求存储资源的一种方式。当某个 PVC 处于 `Pending` 状态时，意味着集群无法满足对该存储资源的需求。这可能是由于可用存储资源不足、存储类引用错误，或者底层存储提供程序出现故障所导致的。

*Diagnosing the Problem*
要诊断 PVC 问题，首先可以使用 `kubectl describe pvc <pvc-name>` 来检查 PVC 的状态和事件。查找任何错误信息或线索，这些可能有助于确定问题的原因。如果 PVC 引用了某个特定的存储类，请确保该存储类确实存在，并且配置正确。

*Fixing PVC Issues*
如果问题与容量有关，可以考虑调整存储资源的规模或修改 PVC 请求。如果问题是配置方面的问题，请检查存储类和供应器的设置，确保它们符合你的 PVC 需求。

#### Applications Not Behaving as Expected
*Cheking application Logs*
当应用程序表现不符合预期时，第一步就是检查应用程序的日志。你可以通过 `kubectl logs <pod-name>` 来访问这些日志。寻找任何错误信息或异常行为，这些都可能帮助我们发现问题的所在。

*inspecting k8s Objects*
接下来，请检查构成您应用程序部署的 Kubernetes 对象。这些对象包括部署、Pod、服务、配置映射等，以及应用程序依赖的其他资源。使用 `kubectl get` 和 `kubectl describe` 命令来获取这些对象的详细信息，确保它们被正确配置。

### Kubernetes 调试最佳实践
#### 使用描述性强且有意义的标签
标签是用于组织和选择 Kubernetes 对象（如 Pod 和服务）的键值对。在 Kubernetes 中，使用具有描述性和意义的标签是一种良好的实践，因为这能帮助你快速识别出与特定应用程序、环境或部署过程中的不同阶段相关的资源。
想象一下，你正在处理一个由多个组件组成的应用程序，这些组件分布在数十个容器上。如果你为这些容器赋予了清晰、有意义的标签，那么你就可以过滤日志和指标数据，从而准确地了解某个特定组件当前的状态。这种细粒度的查询方式能够简化故障排查工作，让你能够专注于与自身基础设施相关的那一部分问题。

#### 监控资源使用情况
在 Kubernetes 环境中，监控资源使用情况对于调试来说至关重要。这有助于了解应用程序如何消耗 CPU、内存以及其他系统资源，这对于诊断与性能和可靠性相关的问题非常有帮助。你可以使用 Prometheus 和 Grafana 等工具来构建监控解决方案，从而实时了解集群的健康状况。
通过 Prometheus，你可以收集 Kubernetes 集群中各个节点的资源使用相关的时间序列数据。这些数据可以使用 Grafana 进行可视化展示，Grafana 拥有强大的图表生成功能，并且能够创建自定义仪表盘。通过监控这些指标，你可以发现一些趋势和模式，这些可能预示着潜在的问题，比如内存泄漏或 CPU 占用过高等问题。

#### 隔离资源以最小化对集群其他部分的影响
在处理问题时，重要的是要尽量减少该问题对整个集群的影响。可以通过使用 Kubernetes 的命名空间来创建隔离的环境，同时通过资源配额来控制每个命名空间或应用程序可使用的集群资源总量。
命名空间为您的应用程序和服务提供了安全的隔离环境。如果您在一个命名空间中遇到了问题，那并不一定会影响其他命名空间中的资源。这种隔离特性在调试过程中非常有用，因为它允许您在一个受控的环境中解决问题，而不会影响到整个集群的稳定性。



## k8s CNI
容器网络接口（Container Network Interface，简称 CNI）是一种标准化的框架，用于配置 Linux 容器中的网络接口。它定义了如 containerd 或 CRI-O 这样的容器运行时如何调用网络插件来将容器连接到网络、分配 IP 地址以及配置路由。需要注意的是，CNI 本身并不提供网络功能，而是规定了插件如何与 Kubernetes 等编排系统进行集成。
当创建一个容器时，容器运行时会调用一个 CNI 插件，并发送诸如 `ADD` 、 `DEL` 或 `CHECK` 这样的命令。该插件随后会配置容器命名空间内的网络接口，分配 IP 地址，并更新路由规则。这种模块化设计使得 Kubernetes 能够支持多种网络实现方式，而无需修改核心组件。

常见k8s CNI网络模型
- Encapsulated overlay networks e.g. VXLAN IP-in-IP
- Unencapsulated routed/BGP networks
- eBPF-based networking models
- Cloud-provider and managed k9s CNIs

### k8s网络详解

Kubernetes 是由谷歌公司开发的一个开源容器编排平台。它用于管理和自动化跨多个机器集群的应用程序容器部署工作。Kubernetes 使得人们能够操作、调度、监控和维护容器化工作负载。

Kubernetes 还可以用于网络管理，使得管理员能够将在不同云基础设施中的工作负载进行迁移，包括公共云、私有云和混合云等。Kubernetes 还允许开发者使用他们喜欢的基础设施来快速打包和部署应用程序，这对于开发新版本的应用程序非常有用。

那些由供应商管理的 Kubernetes 服务通常被描述为“容器即服务”模式，也就是说，供应商会代表您来操作编排层的工作。
这些功能同样适用于 Kubernetes 的多集群环境，在这些环境中，工作负载和网络策略可以分布在不同区域或云提供商的多个集群中。
通过 Kubernetes 网络功能，Kubernetes 组件可以与其他应用程序进行通信，甚至可以相互之间通信。Kubernetes 与其他网络平台的区别在于其采用了扁平化的网络结构，这意味着主机端口无需映射到容器端口。这使得我们能够在一个分布式系统中运行应用程序，而无需进行动态的端口分配。
因为 CNI 插件负责控制容器之间的连接、隔离以及流量路由方式，所以选择哪种插件会对容器安全产生直接的影响，进而决定网络策略、分段管理以及东西向流量控制如何在整个集群中得以实施。网络设计只是 Kubernetes 安全机制的一部分，Kubernetes 的安全机制还包括工作负载隔离、镜像完整性保障以及运行时威胁检测等功能。
最初，容器（Pod）并没有网络接口。为了为容器创建网络接口，容器运行时会向 CNI 插件发送 ADD 命令。容器运行时可以通过诸如 ADD、DEL 和 CHECK 之类的命令来调用该插件。一旦新的网络接口被创建出来，就会有一份 JSON 格式的数据被发送给 CNI 插件，其中包含需要添加的内容的详细信息

### 为什么选择k8s 的CNI接口
无论是 Linux 容器还是容器网络技术，都在不断发展和完善，以满足在不同环境中运行的应用程序的需求。CNI 是 Cloud-Native Computing Foundation（CNCF）推出的一个标准，它规定了 Linux 容器网络接口的配置方式。

CNI 的创建旨在使网络解决方案能够与各种容器编排系统和运行时环境进行集成。与其让网络解决方案具有可插拔性，不如为网络层和容器执行层定义一个统一的接口标准。

CNI 专注于容器网络的连通性问题，以及在处理完容器生命周期后释放所分配的资源。这种专注使得 CNI 的规范更加简洁明了，从而能够被广泛采用。关于 CNI 的更多详细信息，可以在其 GitHub 项目中进行查阅，其中包括使用该规范的第三方插件和运行时环境等相关内容。

### 在 CNI 中使用了哪些网络模型？

*Encapsulated Networks 封装式网络*
该模型通过在现有的三层网络拓扑结构中封装一层逻辑性的二层网络，从而覆盖多个 Kubernetes 节点。二层网络是隔离的，因此无需进行路由分配。其开销成本极低，同时还能提供更好的处理性能以及更大的 IP 数据包容量——这种覆盖封装方式会生成一个 IP 头部，从而构成完整的 IP 数据包。
UDP 端口在 Kubernetes 中的工作节点之间传输封装数据，将网络控制平面的信息传递给相应的 MAC 地址。常见的封装网络模型包括 VXLAN 和互联网协议安全（IPsec）。
简单来说，这个模型充当了一个桥梁，连接了 Kubernetes 的 worker 和 pod。在 pod 内部，负责通信管理的组件是 Docker，或者其他容器引擎。这种方案适用于那些需要二层桥接的场景，因为二层桥接对 Kubernetes worker 的延迟非常敏感。对于位于不同地理位置的数据中心来说，尽量减少它们之间的延迟是非常重要的，这样才能避免网络分割问题。

遵循这种网络模式的 CNI 网络提供商包括 Canal、Flannel 和 Weave 等

*Unencapsulated Networks*

该模型提供了一个第 3 层网络，用于在容器之间路由数据包。虽然不存在独立的第 2 层网络或额外开销，但这样做需要消耗 Kubernetes 工作节点的资源，因为这些节点必须负责处理所需的路由分配工作。为了实现节点之间的连接，采用了某种网络协议，并使用 BGP 协议来将路由信息传递给各个容器。而在各个容器内，负责与工作负载通信的组件则是 Docker 或其他容器引擎

该模型涉及在 Kubernetes 工作节点之间扩展网络路由器，这个路由器负责提供关于如何访问 Pod 的信息。非封装式的网络结构更适合那些偏好基于路由的第三层网络的应用场景。Kubernetes 工作节点的路由会在操作系统级别进行动态更新，从而减少延迟。

*CNI and eBPF-Based Networking*
eBPF（扩展的伯克利数据包过滤器）是 Linux 内核的一项技术，它允许程序在响应网络数据包、系统调用等事件时运行，而无需修改内核代码。在容器网络环境中，eBPF 能够在内核级别实现动态的数据包处理与流量控制，因此比基于 iptables 或 IPVS 的传统方法更加高效且灵活。
现代的 CNI 实现越来越倾向于将 eBPF 作为默认的数据平面。与依赖静态配置或 BGP 等路由协议的 overlay 或 underlay 模型不同，eBPF 能够动态地检查、过滤和路由流量，同时具有较低的开销和更高的可见性。它可以在不离开内核空间的情况下执行网络策略、监控数据包流以及管理 NAT 功能。
插件和政策引擎还决定了 Kubernetes 如何将流量从集群中导出，以传递给外部 API、数据库和互联网端点。
基于 eBPF 的 CNI 技术的一个关键优势是性能表现。由于数据包处理在内核级别进行，因此延迟大大减少，同时 CPU 使用率也降到最低水平。eBPF 还提供了精细的可观测性能力，使得工具能够收集详细的性能指标，并追踪服务与容器之间的流量路径，而无需进行复杂的 instrumentation 操作。
由于具有灵活性和高效性，eBPF 非常适合那些需要高吞吐量、细粒度安全策略以及实时可观测性的 Kubernetes 集群。随着 Kubernetes 的扩展，eBPF 为传统网络架构提供了一种更可扩展且可编程的解决方案。

*Cloud-Provider and Managed k8s CNIs*

云提供商提供自己的 CNI 插件，这些插件经过定制，能够与他们的托管 Kubernetes 服务无缝协作。这些 CNI 插件针对底层云基础设施进行了优化，能够更好地与本地网络、安全以及监控工具集成


## What  is network policy
网络策略是保护 Kubernetes 网络的主要工具。它使得你能够轻松控制集群中的网络流量，只允许传输你希望通过的流量。

要了解网络策略的重要性，我们先来简要了解一下在采用网络策略之前，如何实现网络安全。历史上，在企业网络中，网络安全是通过设计网络设备的物理拓扑结构来实现的（如交换机、路由器、防火墙等），并对其进行相应的配置。这种物理拓扑结构决定了网络的安全边界。在虚拟化的初期阶段，同样的网络和设备结构被虚拟化到了云端，同时采用相同的技术来创建特定的网络拓扑结构，从而确保网络安全。当引入新的应用或服务时，通常需要对网络拓扑结构和网络设备配置进行相应的调整，以满足安全需求。

相比之下，Kubernetes 的网络模型采用“扁平化”的网络结构，每个容器都可以通过容器的 IP 地址与集群中的其他容器进行通信。这种架构大大简化了网络设计，使得新的工作负载可以动态地部署在集群的任何位置，而无需依赖于现有的网络设计。
在这种模型中，网络安全不再由网络拓扑结构来决定，而是通过独立于网络拓扑结构的网络策略来定义。这些网络策略通过标签选择器来实现，从而将网络中的工作负载之间的关系抽象出来，而不需要依赖 IP 地址或 IP 地址范围来进行区分。

### Why is network policy important
在这个攻击者越来越熟练的時代，网络安全作为防御手段的重要性比以往任何时候都要突出。
虽然你可以（并且应该）使用防火墙来限制网络边界处的流量（通常称为南北方向流量），但由于 Pod 的调度和 IP 地址具有动态特性，防火墙对 Kubernetes 流量的监控通常只能达到整个集群的级别，而无法精确到具体的 Pod 群体。此外，大多数攻击者在成功进入网络边界后，通常会试图横向移动以访问更高价值的目标，而基于边界的防火墙无法监控这种横向移动。

另一方面，网络策略的设计旨在适应 Kubernetes 的动态特性。它遵循 Kubernetes 的标准模式，使用标签和选择器来定义 Pod 的组，而不是使用 IP 地址。由于网络策略是在集群内部执行的，因此它能够同时管理南北向和东西向的数据流量。
网络策略代表了网络安全领域的重要发展。它不仅能够应对现代微服务的动态特性，还让开发人员和 DevOps 工程师能够轻松定义网络安全规则，而无需了解复杂的网络管理细节，或者向负责防火墙管理的团队提交工单。通过网络策略，可以轻松定义各种权限需求，例如“只有这个微服务才能连接到数据库”。这些规则可以编写成代码（通常保存在 YAML 文件中），并将网络策略的创建过程整合到 Git 工作流程和持续集成/持续部署流程中。

### Kubernetes network policy
Kubernetes 网络策略的主要特性包括：
- 这些策略是针对命名空间进行限定的（也就是说，你必须在特定命名空间的上下文中创建这些策略，比如与 Pod 类似的情况）。
- 这些策略是通过使用标签选择器来应用于Pod
- 策略规则可以指定允许从其他Pod、命名空间或CIDR地址发送的流量
- 策略规则可以指定使用哪些协议（比如TCP、UDP、SCTP），以及特定的命名端口或者端口号
Kubernetes 本身并不强制执行网络策略，而是将这一职责委托给网络插件来处理。大多数网络插件都实现了 Kubernetes 网络策略的核心功能，不过并非所有插件都包含了该规范中的所有功能。（Calico 插件实现了所有功能，并且是 Kubernetes 网络策略的原始参考实现。）
