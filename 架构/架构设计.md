

## 弹力设计

### 弹力设计总图

首先，我们的服务不能是单点，所以，我们需要在架构中冗余服务，也就是说有多个服务的副本。这需要使用到的具体技术有：
- 负载均衡 + 服务健康检查–可以使用像 Nginx 或 HAProxy 这样的技术；
- 服务发现 + 动态路由 + 服务健康检查，比如 Consul 或 ZooKeeper；
- 自动化运维，Kubernetes 服务调度、伸缩和故障迁移。
然后，我们需要隔离我们的业务，要隔离我们的服务我们就需要对服务进行解耦和拆分

- bulkheads 模式：业务分片 、用户分片、数据库拆分。
- 自包含系统：所谓自包含的系统是从单体到微服务的中间状态，其把一组密切相关的微服务给拆分出来，只需要做到没有外部依赖就行。
- 异步通讯：服务发现、事件驱动、消息队列、业务工作流。
- 自动化运维：需要一个服务调用链和性能监控的监控系统。
接下来，我们就要进行和能让整个架构接受失败的相关处理设计，也就是所谓的容错设计。
- 错误方面：调用重试 + 熔断 + 服务的幂等性设计。
- 一致性方面：强一致性使用两阶段提交、最终一致性使用异步通讯方式。
- 流控方面：使用限流 + 降级技术。
- 自动化运维方面：网关流量调度，服务监控。
![[Pasted image 20250430151319.png]]

1. 冗余服务。通过冗余服务的复本数可以消除单点故障。这需要服务发现，负载均衡，动态路由和健康检查四个功能或组件。
2. 服务解耦。通过解耦可以做到把业务隔离开来，不让服务间受影响，这样就可以有更好的稳定性。在水平层面上，需要把业务或用户分片分区（业分做隔离，用户做多租户）。在垂直层面上，需要异步通讯机制。因为应用被分解成了一个一个的服务，所以在服务的编排和聚合上，需要有工作流（像 Spring 的 Stream 或 Akka 的 flow 或是 AWS 的Simple Workflow）来把服务给串联起来。而一致性的问题又需要业务补偿机制来做反向交易。
3. 服务容错。服务容错方面，需要有重试机制，重试机制会带来幂等操作，对于服务保护来说，熔断，限流，降级都是为了保护整个系统的稳定性，并在可用性和一致性方面在出错的情况下做一部分的妥协。

### 评估web架构的关键属性
HTTP协议应当在以下属性中取得可接受的均衡：
1. 性能 `Performance`: 影响高可用的关键因素
2. 可伸缩性 `Scalability`: 支持部署可以相互交互的大量组件
3. 简单性 `Simplicity`: 易理解、易实现、易验证
4. 可见性能 `Visiable`: 对两个组件间的交互进行监视或者仲裁的能力。如缓存、分层设计等
5. 可移植性 `Portability`: 在不同的环境下运行的能力
6. 可靠性 `Reliability`: 出现故障时，对整体的影响的程度
7. 可修改性 `Modifiability`: 对系统做出修改的难易程度，由可进化性、可定制性、可扩展性、可配置性、可重用性构成

## 软件架构类型
![[PixPin_2026-08-31_19-38-05.png]]

结合你之前关注的 API 性能（缓存/连接池）、K8s/云原生、MCX 网络隔离及 SQL 数据层，这段文字引出了“架构速查表（Cheat Sheet）”的核心价值。以下是解读与实战映射：

### 1. 原文核心主旨解读

- **架构的基石作用**：架构是系统设计的蓝图，定义了组件交互方式，并提供解决常见问题的复用方案，从而提升系统的健壮性与可维护性。
- **选型的困境**：架构风格与模式繁多，辨别最适配特定项目的方案需要时间成本。
- **速查表的价值**：旨在提供一份浓缩指南，帮助快速回顾各架构风格与模式的核心特征，辅助做出理性的架构决策。

### 2. 结合历史语境：架构如何支撑“性能与无感”

回顾你之前的探讨，优秀的架构选型正是这些目标的载体：

- **API 性能层**：采用**微服务/网关架构**，叠加连接池、异步日志、JWT 认证与 Redis 缓存，解决高并发 I/O 瓶颈。
- **网络与云原生**：K8s 编排 + 服务网格（Istio/eBPF）实现**拓扑感知与无感观测**；MCX 专网中，通过“默认 APN 复用”实现业务无感兼容，或“专用 APN”实现强隔离。
- **数据层**：合理运用 INNER/LEFT JOIN 与 ORM 优化，配合回归/Fuzz 测试保障数据完整性。

### 3. 架构风格速查表（融合你的实战场景）

|架构风格/模式|核心特征|典型适用场景（结合历史）|优势与权衡|
|---|---|---|---|
|**单体架构 (Monolithic)**​|所有组件打包部署，内聚性强|内部低敏工具、简单运维接口（API Key）|开发简单；但扩展难，易成“巨石”|
|**微服务 (Microservices)**​|服务拆分、独立部署、API 交互|K8s 集群、API 网关、JWT/OAuth 认证|弹性好、技术栈灵活；需解决网络延迟与治理|
|**事件驱动 (Event-Driven)**​|异步消息、解耦（Kafka/Pulsar）|日志削峰、MCX 信令异步化、缓存同步|高吞吐、削峰填谷；一致性挑战|
|**分层/六边形 (Layered/Hex)**​|关注点分离、依赖倒置|核心业务（MCX 逻辑）与边缘（APN 适配）隔离|可维护性强；增加抽象层开销|
|**Serverless/FaaS**​|按需执行、无状态、免运维|轻量 API、定时任务、边缘计算|极致弹性；冷启动、厂商锁定|
|**网关/边车 (Gateway/Sidecar)**​|流量拦截、协议转换、QoS|APISIX 缓存、Istio 多路复用、eBPF 观测|业务无感增强；增加网络跳数|

### 4. 架构决策：如何平衡“安全、性能与易用”

面对“哪种最有效”的终极问题，结合速查表，实战中的架构决策往往是**混合体**：

- **核心域**：用微服务 + 事件驱动，保障高并发与解耦（连接池/异步日志兜底）。
- **接入层**：用网关/服务网格，统一认证（OIDC/JWT）、负载压缩（gzip）、缓存与限流。
- **数据域**：SQL 关联（JOIN）+ Redis 缓存，配合网络隔离（默认/专用 APN）保障传输安全。
- **观测与测试**：eBPF 无感 Profiling + 回归/Fuzz 测试，贯穿架构全生命周期。

## CAP, BASE, SOLID, KISS, What do these acronyms mean?
![[PixPin_2026-08-31_19-56-40.png]]

### CAP

CAP 定理指出，任何分布式数据存储都只能提供以下三项保证中的两项：

1. 一致性（Consistency）- 每次读取都能获取到最新的写入数据或报错。
2. 可用性（Availability）- 每次请求都能收到响应。
3. 分区容错性（Partition tolerance）- 系统在网络故障时仍能继续运行。

然而，这一定理因对分布式系统而言过于狭隘而受到批评，我们不应将其用于数据库分类。在分布式系统中，网络故障是必然发生的，我们必须在任何分布式系统中应对这一问题。

你可以在 Martin Kleppmann 的《请停止将数据库称为 CP 或 AP》（"Please stop calling databases CP or AP"）中阅读更多相关内容。

### BASE

关系型数据库中使用的 ACID（原子性-一致性-隔离性-持久性）模型对 NoSQL 数据库来说过于严格。BASE 原则提供了更大的灵活性，选择可用性而非一致性。它指出系统状态最终将保持一致（最终一致性）。

### SOLID

SOLID 原则在面向对象编程（OOP）中非常著名。它包含 5 个组成部分：

1. SRP（单一职责原则）- 每个代码单元应只有一个职责。
2. OCP（开闭原则）- 代码单元应对扩展开放，但对修改关闭。
3. LSP（里氏替换原则）- 子类应能被其基类替换。
4. ISP（接口隔离原则）- 暴露具有特定职责的多个接口。
5. DIP（依赖倒置原则）- 使用抽象来解耦系统中的依赖关系。

### KISS

“保持简单，傻瓜！”（"Keep it simple, stupid!"）是美军海军在 1960 年首次提出的设计原则。它指出大多数系统在保持简单时运行得最好。

## What is Semantic Versioning
![[Pasted image 20260902095250.png]]

Semantic Versioning (SemVer) is a versioning scheme for software that aims to convey meaning about the underlying changes in a release.  
语义版本制（SemVer）是一种用于软件版本的方案，其目的是传达版本发布中发生的各种变化的含义。

- SemVer uses a three-part version number: MAJOR.MINOR.PATCH.  
    SemVer 采用三部分版本号格式：MAJOR.MINOR.PATCH。
    - **MAJOR version**: Incremented when there are incompatible API changes.  
        主要版本：在出现不兼容的 API 变更时会增加更新频率。
    - **MINOR version**: Incremented when functionality is added in a backward-compatible manner.  
        次要版本：在功能以向后兼容的方式被添加时，该版本会有所增强。
    - **PATCH version**: Incremented when backward-compatible bug fixes are made.  
        补丁版本：在修复了与旧版本兼容的漏洞后，会进行更新。
- **Example Workflow  示例工作流程**
    - **Initial Development Phase  
        初期开发阶段**
        - Start with version 0.1.0.  
            从版本 0.1.0 开始。
    - **First Stable Release  首次稳定版本发布**
        - Reach a stable release: 1.0.0.  
            期待稳定版本的发布：1.0.0
    - **Subsequent Changes  后续的变化**
        - **Patch Release**: A bug fix is needed for 1.0.0. Update to 1.0.1.  
            版本更新：1.0.0 版本存在漏洞需要修复。请升级到 1.0.1 版本。
        - **Minor Release**: A new, backward-compatible feature is added to 1.0.3. Update to 1.1.0.  
            minor 版本发布：在 1.0.3 版本中新增了一个与旧版本兼容的新功能。请升级到 1.1.0 版本。
        - **Major Release**: A significant change that is not backward-compatible is introduced in 1.2.2. Update to 2.0.0.  
            重大版本发布：在 1.2.2 版本中引入了一项重要的变更，但该变更并不与旧版本兼容。后续更新至 2.0.0 版本。
    - **Special Versions and Pre-releases  
        特别版本和预发布产品**
        - **Pre-release Versions**: 1.0.0-alpha, 1.0.0-beta, 1.0.0-rc.1.  
            预发布版本：1.0.0-alpha、1.0.0-beta、1.0.0-rc.1。
        - **Build Metadata**: 1.0.0+20130313144700.  
            构建元数据：1.0.0+20130313144700。

##  8 Key Concepts in Domain-Driven Design
![[Pasted image 20260902101322.png]]

Domain-driven design advocates driving the design of software through domain modeling.  
领域驱动设计主张通过领域建模来推动软件设计的过程。

Unified language is one of the key concepts of domain-driven design. A domain model is a bridge across the business domains.  
统一语言是领域驱动设计中的一个关键概念。领域模型则是一座连接不同业务领域的桥梁。

### Domain Driven Design  领域驱动设计

Domain-driven design advocates driving the design of software through domain modeling.  
领域驱动设计主张通过领域建模来推动软件设计的过程。

Unified language is one of the key concepts of domain-driven design. A domain model is a bridge across the business domains.  
统一语言是领域驱动设计中的一个关键概念。领域模型则是一座连接不同业务领域的桥梁。

### Business Entities  商业实体

The use of models can assist in expressing business concepts and knowledge and in guiding further development of software, such as databases, APIs, etc.  
使用模型可以帮助表达商业概念和知识，并指导软件的其他部分的发展，比如数据库、API 等。

### Model Boundaries  模型边界

Loose boundaries among sets of domain models are used to model business correlations.  
在多个领域模型之间建立宽松的边界，可以用来模拟业务之间的关联关系。

### Aggregation  聚合

An Aggregate is a cluster of related objects (entities and value objects) that are treated as a single unit for the purpose of data changes.  
聚合是指一组相关的对象（包括实体和价值对象），这些对象被当作一个单一单元来处理，以便于数据的操作。

### Entities vs. Value Objects  
实体与值对象

In addition to aggregate roots and entities, there are some models that look like disposable, they don’t have their own ID to identify them, but are more as part of some entity that expresses a collection of several fields.  
除了聚合根和实体之外，还有一些模型看起来像是可丢弃的对象。它们没有自己的标识符来识别，而是作为某个实体的组成部分，该实体包含多个字段的集合。

### Operational Modeling  操作建模

In domain-driven design, in order to manipulate these models, there are a number of objects that act as “operators”.  
在领域驱动设计中，为了操作这些模型，有许多对象充当“操作符”的角色。

### Layering the architecture  
构建分层架构

In order to better organize the various objects in a project, we need to simplify the complexity of complex projects by layering them like a computer network.  
为了更好地组织项目中的各种元素，我们需要像处理计算机网络那样，将复杂项目进行分层处理，从而简化其复杂性。

### Build the domain model  
构建领域模型

Many methods have been invented to extract domain models from business knowledge.  
已经发明了许多方法，用于从商业知识中提取领域模型。

## Orchestration vs. Choreography in Microservices  
在微服务架构中，编排与编舞的区别
![[Pasted image 20260902101732.png]]

How do microservices collaborate and interact with each other?  
微服务之间是如何协作和相互交流的呢？

There are two ways: 𝐨𝐫𝐜𝐡𝐞𝐬𝐭𝐫𝐚𝐭𝐢𝐨𝐧 and 𝐜𝐡𝐨𝐫𝐞𝐨𝐠𝐫𝐚𝐩𝐡𝐲.  
有两种方法：𝐨𝐫𝐜𝐡𝐞𝐬𝐭𝐫𝐚𝐭𝐢𝐨𝐧和𝐜𝐡𝐨𝐫𝐞𝐨𝐠𝐫𝐚𝐩𝐡𝐲。

Choreography is like having a choreographer set all the rules. Then the dancers on stage (the microservices) interact according to them. Service choreography describes this exchange of messages and the rules by which the microservices interact.  
编舞就像是由一位编舞者制定所有的规则。然后，舞台上的舞者（即各个微服务）根据这些规则进行互动。服务编舞描述了这种信息交换机制，以及微服务之间互动的规则。

Orchestration is different. The orchestrator acts as a center of authority. It is responsible for invoking and combining the services. It describes the interactions between all the participating services. It is just like a conductor leading the musicians in a musical symphony. The orchestration pattern also includes the transaction management among different services.  
编排则有所不同。编排器扮演着权威中心的角色，它负责调用和整合各种服务。它描述了所有参与服务的之间如何相互协作。这就好比指挥家在交响乐中引导乐手们演奏一样。这种编排模式还涵盖了不同服务之间的事务管理。

三星：在某种程度上很重要。你可能不需要知道具体的实现细节。

One-star: Advanced. Good to know for senior candidates.  
一星：高级。对资深候选人来说，这很有帮助。

## Foundational Patterns  基础模式

These patterns are the fundamental principles for applications to be automated on k8s, regardless of the application’s nature.  
这些模式是在 K8S 上进行自动化应用的基本准则，无论应用的性质如何。

- **Health Probe Pattern  健康调查模式**
    
    This pattern requires that every container must implement observable APIs for the platform to manage the application.  
    这种模式要求每个容器都必须实现可观察性 API 接口，以便平台能够管理应用程序。
    
- **Predictable Demands Pattern  
    可预测的需求模式**
    
    This pattern requires that we should declare application requirements and runtime dependencies. Every container should declare its resource profile.  
    这种模式要求我们必须声明应用程序的需求以及运行时的依赖项。每个容器都应该声明自己的资源配置文件。
    
- **Automated Placement Pattern  
    自动化放置模式**
    
    This pattern describes the principles of Kubernetes’ scheduling algorithm.  
    这种模式描述了 Kubernetes 调度算法的原理。
    

## Structural Patterns  结构模式

These patterns focus on structuring and organizing containers in a Pod.  
这些模式专注于在 Pod 中构建和组织容器。

- **Init Container Pattern  初始化容器模式**
    
    This pattern has a separate life cycle for initialization-releated tasks.  
    这种模式为与初始化相关的任务定义了一个独立的生命周期。
    
- **Sidecar Pattern  侧车模式**
    
    This pattern extends a container’s functionalities without changing it.  
    这种模式可以在不修改容器功能的情况下扩展其能力。
    

## Behavioral Patterns  行为模式

These patterns describe the life cycle management of a Pod. Depending on the type of the workload, it can run as a service or a batch job.  
这些模式描述了 Pod 的生命周期管理。根据工作负载的类型，Pod 可以以服务的形式运行，也可以作为批处理任务来执行。

- **Batch Job Pattern  批处理作业模式**
    
    This pattern is used to manage isolated atomic units of work.  
    这种模式用于管理独立的原子级工作单元。
    
- **Stateful Service Pattern  有状态服务模式**
    
    This pattern creates distributed stateful applications.  
    这种模式能够创建出分布式的有状态应用程序。
    
- **Service Discovery Pattern  
    服务发现模式**
    
    This pattern describes how clients discover the services.  
    这种模式描述了客户端如何找到这些服务。
    

## Higher-Level Patterns  更高层次的模式

These patterns focus on higher-level application management.  
这些模式专注于更高层次的应用管理。

- **Controller Pattern  控制器模式**
    
    This pattern monitors the current state and reconciles with the declared target state.  
    该模式用于监控当前状态，并将其与所宣称的目标状态进行比对。
    
- **Operator Pattern  操作符模式**
    
    This pattern defines operational knowledge in an algorithmic and automated form.  
    这种模式将操作知识以算法化和自动化的形式进行了定义。
